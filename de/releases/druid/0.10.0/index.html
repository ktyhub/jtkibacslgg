Druide Druide-0.10.0

Druid 0.10.0 enthält Hunderte von Leistungsverbesserungen, Stabilitätsverbesserungen und Fehlerbehebungen von über 40 Mitwirkenden. Zu den wichtigsten neuen Funktionen gehören eine integrierte SQL-Ebene, numerische Dimensionen, Unterstützung der Kerberos-Authentifizierung, eine Überarbeitung der „Index“-Aufgabe, ein neuer „Gefällt mir“-Filter, große Spalten, die Möglichkeit, den Koordinator und den Overlord als einen einzigen Dienst auszuführen, leistungsstärkere Standardeinstellungen und acht neue Erweiterungen. Wenn Sie ein Upgrade von einer früheren Version von Druid durchführen, finden Sie unten „Aktualisierung von 0.9.2 und früher“ Hinweise zum Upgrade, einschließlich einiger abwärtsinkompatibler Änderungen. Die vollständige Liste der Änderungen finden Sie hier: https://github.com/druid-io/druid/pulls?utf8=%E2%9C%93&q=is%3Apr%20is%3Aclosed%20milestone%3A0.10.0 Die Dokumentation für diese Version finden Sie unter: http://druid.io/docs/0.10.0/

Highlights

Integriertes SQL

Druid enthält jetzt einen integrierten SQL-Server, der von Apache Calcite unterstützt wird. Druid bietet zwei SQL-APIs: HTTP POST und JDBC. Dies stellt eine Alternative zu Druids nativem JSON API dar, das neuen Entwicklern vertrauter ist und die Integration bereits vorhandener Anwendungen, die nativ SQL sprechen, erleichtert. In dieser ersten Version werden nicht alle Druid- und SQL-Funktionen von der SQL-Ebene unterstützt, wir beabsichtigen jedoch, beide in zukünftigen Versionen zu erweitern. Die SQL-Unterstützung kann durch die Einstellung druid.sql.enable=true in Ihrer Konfiguration aktiviert werden. Einzelheiten und Dokumentation finden Sie unter http://druid.io/docs/0.10.0/querying/sql.html. Hinzugefügt in #3682 von @gianm.

Numerische Bemaßungen

Druid unterstützt jetzt numerische Dimensionen zum Zeitpunkt der Aufnahme und Abfrage. Benutzer können Long- und Float-Spalten als Dimensionen aufnehmen (d. h. die numerischen Spalten als Teil des Gruppierungsschlüssels für die Aufnahmezeit statt als Aggregatoren behandeln, wenn Rollup aktiviert ist). Darüber hinaus können Druid-Abfragen jetzt jede beliebige Long- oder Float-Spalte als Dimension zum Gruppieren oder Filtern akzeptieren. Es gibt Leistungseinbußen zwischen Zeichenfolgen- und numerischen Spalten. Numerische Spalten lassen sich im Allgemeinen schneller gruppieren als Zeichenfolgenspalten. Numerische Spalten haben keine Indizes, daher ist die Filterung nach ihnen im Allgemeinen langsamer als nach Zeichenfolgenspalten. Siehe http://druid.io/docs/0.10.0/ingestion/schema-design.html#numeric-dimensions für die Erfassungsdokumentation und http://druid.io/docs/0.10.0/querying/dimensionspecs.html für die Abfragedokumentation. Hinzugefügt in #3838, #3966 und anderen Patches von @jon-wei.

Unterstützung der Kerberos-Authentifizierung

Eine neue Erweiterung namens „druid-kerberos“ wurde hinzugefügt, die Unterstützung für die Benutzerauthentifizierung für Druid-Knoten mithilfe von Kerberos hinzufügt. Es nutzt den einfachen und geschützten Aushandlungsmechanismus GSSAPI, SPNEGO(https://en.wikipedia.org/wiki/SPNEGO) für die Authentifizierung über HTTP. Dokumentation zum Konfigurieren der Kerberos-Authentifizierung finden Sie unter http://druid.io/docs/0.10.0/development/extensions-core/druid-kerberos.html. Hinzugefügt in #3853 von @nishantmonu51.

Überarbeitung der Indexaufgabe

Die Indizierungsaufgabe wurde neu geschrieben, um die Leistung zu verbessern, insbesondere für Jobs, die sich über mehrere Intervalle erstrecken und viele Shards generiert haben. Die SegmentGranularität intervals kann jetzt automatisch ermittelt werden und muss nicht mehr angegeben werden. Die Aufnahmezeit kann jedoch reduziert werden, wenn sowohl intervals als auch numShards bereitgestellt werden. Darüber hinaus unterstützt die Indizierungsaufgabe jetzt ein appendToExisting-Flag, das bewirkt, dass die Daten als zusätzlicher Shard der aktuellen Version indiziert werden und nicht als neue Version, die die vorherige Version überschattet. Dokumentation finden Sie unter http://druid.io/docs/0.10.0/ingestion/tasks.html#index-task. Hinzugefügt in #3611 von @dclim.

Like-Filter

Druid enthält jetzt einen „Gefällt mir“-Filter, der eine Filterung im SQL-LIKE-Stil ermöglicht, z. B. foo LIKE 'bar%'. Die Implementierung ist im Allgemeinen schneller als Regex-Filter und wird nach Möglichkeit gegenüber Regex-Filtern empfohlen. Insbesondere sind Like-Filter für Präfixe wie bar% deutlich schneller als entsprechende Regex-Filter wie ^bar.*. Dokumentation finden Sie unter http://druid.io/docs/0.10.0/querying/filters.html#like-filter. Hinzugefügt in #3642 von @gianm.

Große Spalten

Druid unterstützt jetzt einzelne Spalten, die größer als 2 GB sind. Diese Funktion ist normalerweise nicht erforderlich, da allgemein empfohlen wird, dass Segmente im Allgemeinen eine Größe von 500 MB bis 1 GB haben sollten. Sie ist jedoch in Situationen nützlich, in denen eine Spalte viel größer als alle anderen ist (z. B. bei großen Skizzen). Diese Funktionalität steht allen Druid-Benutzern zur Verfügung und bei Verwendung der integrierten Spaltentypen ist keine spezielle Konfiguration erforderlich. Wenn Sie einen benutzerdefinierten Metrikspaltentyp als Druid-Erweiterung entwickelt haben, können Sie die Unterstützung großer Spalten aktivieren, indem Sie getSerializer in Ihrem ComplexMetricsSerde überschreiben. Hinzugefügt in #3743 von @akashdw.

Kombinationsoption Koordinator/Overlord

Druideneinsätze können jetzt vereinfacht werden, indem die Koordinator- und Overlord-Funktionen im Koordinatorprozess kombiniert werden. Stellen Sie dazu druid.coordinator.asOverlord.enabled und druid.coordinator.asOverlord.overlordService entsprechend auf Ihren Koordinatoren ein und stoppen Sie dann Ihre Overlords. Die Overlord-Konsole wäre auf http://coordinator-host:port/console.html verfügbar. Dies ist derzeit eine experimentelle Funktion und standardmäßig deaktiviert. Wir beabsichtigen, dies in einer zukünftigen Version von Druid als Standard festzulegen. Dokumentation zu dieser Funktion und den Konfigurationsoptionen finden Sie unter http://druid.io/docs/0.10.0/configuration/coordinator.html. Hinzugefügt in #3711 von @himanshug.

Leistungsstärkere Standardeinstellungen

In dieser Version werden zwei Standardeinstellungen geändert, um die Leistung sofort zu verbessern: – Die in Druid 0.9.0 eingeführte Option buildV9Directly ist jetzt standardmäßig aktiviert. Diese Option verbessert die Leistung der Indizierung, indem das v9-Datenformat direkt erstellt wird, anstatt zuerst v8 zu erstellen und dann in v9 zu konvertieren. Bei Bedarf können Sie zum alten Code zurückkehren, indem Sie „buildV9Directly“ in Ihren Indizierungsaufgaben auf „false“ setzen. – Die in Druid 0.9.2 eingeführte v2-GroupBy-Engine ist jetzt standardmäßig aktiviert. Diese neue GroupBy-Engine wurde für eine bessere Leistung und Speicherverwaltung von Grund auf neu geschrieben. Bei Bedarf können Sie ein Rollback zur alten Engine durchführen, indem Sie entweder „druid.groupBy.query.defaultStrategy“ in Ihren runtime.properties oder „groupByStrategy“ in Ihrem Abfragekontext auf „v1“ setzen. Einzelheiten zu den Unterschieden zwischen groupBy v1 und v2 finden Sie unter http://druid.io/docs/0.10.0/querying/groupbyquery.html.

Weitere Leistungsverbesserungen

Neben leistungsstärkeren Standardeinstellungen verfügt Druid 0.10.0 über eine Reihe weiterer Leistungsverbesserungen, darunter: – Präzise Bitset-Vereinigung, Schnittmenge und Iterationsoptimierung (#3883) von @leventov – DimensionSelector-basierte Wertanpassungsoptimierung (#3858) von @leventov – Suchabfragestrategie zur Auswahl der indexbasierten vs. Cursor-basierten Ausführung (#3792) von @jihoonson

  • Optimierung der Bitset-Iteration (#3753) von @leventov – GroupBy-Optimierung für die Granularität „alle“ (#3740) von @gianm – Flush nach jedem DefaultObjectMapper-Schreibvorgang deaktivieren (#3748) von @jon-wei
  • Kurzschließender UND-Filter (#3676) von @gianm – Verbesserte Leistung von IndexMergerV9 (#3440) von @leventov

Aktualisierung von 0.9.2 und früher

Nachfolgend finden Sie die Änderungen zwischen 0.9.2 und 0.10.0, die Sie vor dem Upgrade beachten sollten. Wenn Sie von einer früheren Version als 0.9.2 aktualisieren, lesen Sie bitte die release notes der relevanten Zwischenversionen für zusätzliche Hinweise.

Laufende Updates

Für fortlaufende Updates sollte der von http://druid.io/docs/0.10.0/operations/rolling-updates.html beschriebene Standard-Druid-Update-Prozess befolgt werden.

API-Änderungen abfragen

Bitte beachten Sie, dass sich die folgende abwärtsinkompatible Abfrage API beim Aktualisieren ändert. Einige Abfragen müssen möglicherweise angepasst werden, damit sie sich weiterhin wie erwartet verhalten. – JavaScript-Abfragefunktionen sind jetzt aus Sicherheitsgründen standardmäßig deaktiviert (#3818). Wenn Sie diese Funktionen verwenden, können Sie sie wieder aktivieren, indem Sie in Ihren Laufzeiteigenschaften druid.javascript.enabled=true festlegen. Einzelheiten, einschließlich Sicherheitsaspekte, finden Sie unter http://druid.io/docs/0.10.0/development/javascript.html. – GroupBy-Abfragen erlauben __time nicht mehr als Ausgabenamen einer Dimension, eines Aggregators oder eines Post-Aggregators (#3967). – Wählen Sie Abfrage-PagingSpecs jetzt standardmäßig auf das Verhalten fromNext: true aus, wenn fromNext nicht angegeben ist (#3986). Das Verhalten bleibt bei Auswahlabfragen unverändert, für die fromNext angegeben wurde. Wenn Sie den alten Standard bevorzugen, können Sie dies über die Laufzeiteigenschaft druid.query.select.enableFromNextDefault ändern. Weitere Informationen finden Sie unter http://druid.io/docs/0.10.0/querying/select-query.html. – SegmentMetadata-Abfragen umfassen standardmäßig keine „Größen“-Analyse mehr (#3773). Sie können weiterhin eine „Größen“-Analyse anfordern, indem Sie „size“ zum Zeitpunkt der Abfrage zu „analysisTypes“ hinzufügen.

Bereitstellungs- und Konfigurationsänderungen

Bitte beachten Sie beim Update die folgenden einsatzbezogenen Änderungen.

  • Druid erfordert jetzt Java 8 zum Ausführen (#3914). Wenn Sie derzeit Java 7 verwenden, empfehlen wir, zuerst Java und dann Druid zu aktualisieren.
  • Druid verwendet jetzt standardmäßig die „v2“-Engine für GroupBy und nicht die alte „v1“-Engine. In diesem Zusammenhang wurden die Speichernutzungsgrenzen von zeilenbasierten auf bytebasierte Grenzen geändert, sodass es möglich ist, dass einige Abfragen, die zuvor die Ressourcengrenzen erreichten, diese jetzt überschreiten und fehlschlagen. Sie können dies vermeiden, indem Sie die neue GroupBy-Engine entsprechend optimieren. Bei Bedarf können Sie ein Rollback zur alten Engine durchführen, indem Sie entweder „druid.groupBy.query.defaultStrategy“ in Ihren runtime.properties oder „groupByStrategy“ in Ihrem Abfragekontext auf „v1“ setzen. Weitere Einzelheiten zu den Unterschieden zwischen groupBy v1 und v2 finden Sie unter http://druid.io/docs/0.10.0/querying/groupbyquery.html.<p>Diese neue GroupBy-Engine wurde für eine bessere Leistung und Speicherverwaltung von Grund auf neu geschrieben. Die Abfrage API und die Ergebnisse sind zwischen den beiden Engines kompatibel. Aus Sicht der Clusterkonfiguration gibt es jedoch einige Unterschiede: (1) GroupBy v2 verwendet hauptsächlich Off-Heap-Speicher anstelle von On-Heap-Speicher; (2) es erfordert einen Zusammenführungspuffer für jede gleichzeitige Abfrage; (3) Wenn Sie das Caching für „groupBy“ konfiguriert haben, muss es sich um historische Daten handeln; und (4) es unterstützt chunkPeriod nicht.
  • Druid hat jetzt einen Standardwert ungleich Null für druid.processing.numMergeBuffers (#3953). Dadurch wird die Menge des in der Standardkonfiguration verwendeten Direktspeichers erhöht. Diese Änderung wurde im Zusammenhang mit der Änderung der Standard-GroupBy-Engine vorgenommen, da die neue „v2“-Engine Zusammenführungspuffer erfordert. Wenn Sie bisher GroupBy v1 verwendet haben, sollten Sie dies durch die Reduzierung Ihres JVM-Heaps ausgleichen können, da GroupBy v2 Off-Heap-Speicher anstelle von On-Heap-Speicher verwendet. – Druid-abfragebezogene Prozesse (Broker-, Verlaufs-, Indizierungsaufgaben) weisen jetzt eifrig druid.processing.numThreads Anzahl von DirectByteBuffer-Instanzen der Größe druid.processing.buffer.sizeBytes für die Abfrageverarbeitung beim Start zu (#3628). Diese Zuordnung war in früheren Versionen von Druid verzögert. Diese Änderung wirkt sich nicht auf die Speichernutzung eines Druid-Clusters mit langer Laufzeit aus, bedeutet jedoch, dass beim Start von Druid Speicher für die Verarbeitung von Puffern verfügbar sein muss. – Bei der Ausführung in Nicht-UTC-Zeitzonen ändert sich das Verhalten vordefinierter segmentGranularity-Konstanten wie „Tag“ beim Upgrade. Früher wurden dadurch Segmente anhand lokaler Tage generiert. In Druid 0.10.0 werden dadurch Segmente mit UTC-Tagen generiert. Wenn Sie Druid in der UTC-Zeitzone ausgeführt haben, hat diese Änderung keine Auswirkungen. Bitte beachten Sie, dass die Ausführung von Druid in einer Nicht-UTC-Zeitzone nicht offiziell unterstützt wird (siehe http://druid.io/docs/0.10.0/configuration/index.html) und wir empfehlen, alle Prozesse immer in UTC-Zeitzonen auszuführen. Um lokale Tagessegmente mit Druid 0.10.0 zu erstellen, können Sie eine Segmentgranularität für die lokale Zeit verwenden, wie zum Beispiel:
"segmentGranularity" : {
     "type" : "period",
     "period" : "P1D",
     "timeZone" : "America/Los_Angeles"
}

Erweiterungsänderungen

– Die Schnittstellen AggregatorFactory, BufferAggregator und PostAggregator haben sich geändert (#3894, #3899, #3957, #4071). Wenn Sie eine benutzerdefinierte Erweiterung bereitgestellt haben, die eine AggregatorFactory oder einen PostAggregator enthält, muss diese neu kompiliert werden. Alle integrierten Erweiterungen von Druid wurden im Hinblick auf diese Änderung aktualisiert. – Erweiterungen, die auf Druid 0.10.x abzielen, müssen mit JDK 8 kompiliert werden.
