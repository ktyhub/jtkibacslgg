Druide Druide-0.16.0-incubating

Apache Druid 0.16.0-incubating enthält über 350 neue Funktionen, Leistungsverbesserungen, Fehlerbehebungen und wichtige Dokumentationsverbesserungen von 50 Mitwirkenden. Sehen Sie sich die vollständige Liste der Änderungen und alles, was mit dem Meilenstein markiert ist an.

Highlights

<a name="perf" href="#perf">#</a> Leistung

<a name="vector" href="#vector">#</a> 'Vektorisierte' Abfrageverarbeitung

Neu in 0.16.0 ist eine experimentelle „vektorisierte“ Abfrageausführungs-Engine, die eine Geschwindigkeitssteigerung im Bereich von 1.3-3x für Zeitreihen- und Gruppen-nach-V2-Abfragen ermöglichen kann. Es arbeitet nach dem Prinzip der Stapelverarbeitung von Vorgängen für Zeilen, anstatt jeweils eine einzelne Zeile zu verarbeiten, z. B. Bitmaps stapelweise statt pro Zeile iterieren, Spaltenwerte stapelweise lesen, stapelweise filtern, Werte stapelweise aggregieren usw. Dies führt zu deutlich weniger Methodenaufrufen, einer besseren Speicherlokalität und einer erhöhten Cache-Effizienz. Dies ist eine experimentelle Funktion, aber wir betrachten sie als den Weg nach vorne für die Verarbeitung von Druid-Abfragen und freuen uns über Feedback, während wir in kommenden Versionen weiterhin an der Verbesserung und Ergänzung fehlender Funktionen arbeiten.

  • Nur timeseries und groupBy verfügen über vektorisierte Engines.
  • GroupBy verarbeitet noch keine anderen Mehrwertdimensionen oder Granularitäten als „alle“.
  • Vektorcursor können keine virtuellen Spalten oder absteigende Reihenfolge verarbeiten.
  • Ausdrücke werden nirgendwo unterstützt: nicht als Eingaben für Aggregatoren, in virtuellen Funktionen oder in Filtern.
  • Nur einige Aggregatoren verfügen über vektorisierte Implementierungen: „count“, „doubleSum“, „floatSum“, „longSum“, „hyperUnique“ und „filtered“.
  • Nur einige Filter verfügen über vektorisierte Matcher: „selector“, „bound“, „in“, „like“, „regex“, „search“, „and“, „or“ und „not“.
  • Andere Dimensionsspezifikationen als „Standard“ funktionieren noch nicht (keine Extraktionsfunktionen oder gefilterte Dimensionsspezifikationen). Die Funktion kann aktiviert werden, indem Sie Ihren Abfragekontext auf "vectorize": true festlegen (der Standardwert ist false). Dies funktioniert sowohl für Druid SQL als auch für native Abfragen. Bei der Einstellung true wird nach Möglichkeit die Vektorisierung verwendet; Andernfalls greift Druid auf seine nicht vektorisierte Abfrage-Engine zurück. Sie können es auch auf "force" setzen, wodurch ein Fehler zurückgegeben wird, wenn die Abfrage nicht vollständig vektorisiert werden kann. Dies ist hilfreich, um zu bestätigen, dass tatsächlich Vektorisierung verwendet wird. Sie können die Blockgröße während der Ausführung steuern, indem Sie den Abfragekontextparameter vectorSize festlegen (Standard ist 1000). https://github.com/apache/incubator-druid/issues/7093 https://github.com/apache/incubator-druid/pull/6794

<a name="array-group" href="#array-group">#</a> GroupBy Array-basierte Ergebniszeilen

GroupBy v2-Abfragen verwenden jetzt eine Array-basierte Darstellung der Ergebniszeilen und nicht die kartenbasierte Darstellung, die in früheren Versionen von Druid verwendet wurde. Dies ermöglicht eine schnellere Generierung und Verarbeitung von Ergebnismengen. Im Auslieferungszustand ist diese Änderung unsichtbar und abwärtskompatibel. Sie müssen keine Konfiguration ändern, um die Vorteile dieses effizienteren Formats zu nutzen, und es hat keine Auswirkungen auf die zwischengespeicherten Ergebnisse. Intern wird dieses Format immer automatisch vom Broker in den Abfragen verwendet, die er an historische Daten sendet. Standardmäßig werden die Ergebnisse beim Broker in das vorhandene Kartenformat zurückübersetzt, bevor sie an den client zurückgesendet werden. Wenn Sie jedoch den Mehraufwand dieser Übersetzung vermeiden und noch schnellere Ergebnisse erhalten möchten, können Sie resultAsArray im Abfragekontext festlegen, um das neue Array-basierte Ergebniszeilenformat direkt zu durchlaufen. Das Schema lautet wie folgt in der Reihenfolge:

  • Zeitstempel (optional; nur wenn Granularität != ALLE)
  • Abmessungen (in der Reihenfolge)
  • Aggregatoren (in der Reihenfolge)
  • Post-Aggregatoren (optional; in der Reihenfolge, falls vorhanden) https://github.com/apache/incubator-druid/issues/8118 https://github.com/apache/incubator-druid/pull/8196

<a name="minor-compaction" href="#minor-compaction">#</a> „Kleine“ Komprimierung

Benutzer des Kafka-Indizierungsdienstes und der Kafka-Komprimierung, die ein paar verspätete Daten erhalten, können eine enorme Verbesserung in Form eines neuen Konzepts namens „geringfügige“ Komprimierung feststellen. Die durch interne Änderungen an der Versionierung von Datensegmenten ermöglichte geringfügige Komprimierung basiert auf der Idee einer segmentbasierten Sperrung zum Zeitpunkt der Indizierung anstelle des aktuellen Druid-Sperrverhaltens (das jetzt als „Zeitblock“-Sperre bezeichnet wird). Durch das Sperren von Segmenten können erwartungsgemäß nur die Segmente gesperrt werden, die komprimiert werden, während gleichzeitig neue „angehängte“ Indizierungsaufgaben (wie Kafka-Indizierungsaufgaben) weiterhin ausgeführt und gleichzeitig neue Segmente erstellt werden können. Dies ist ein großes Problem, wenn Sie viele späte Daten erhalten, da das aktuelle Verhalten dazu führt, dass Komprimierungsaufgaben verhungern, da Echtzeitaufgaben mit höherer Priorität die Sperren beanspruchen. Dadurch wird verhindert, dass Komprimierungsaufgaben die Segmentgrößen der Datenquellen optimieren, was zu einer verringerten Gesamtleistung führt. Um die Segmentsperre zu aktivieren, müssen Sie forceTimeChunkLock im Aufgabenkontext auf false oder druid.indexer.tasklock.forceTimeChunkLock=false in der Overlord-Konfiguration festlegen. Vorsicht: Nach der Aktivierung dieser Funktion ist aufgrund der Änderungen in der Segmentversionierung kein Rollback-Pfad integriert, sodass Sie nach dem Upgrade auf 0.16 kein Downgrade auf eine ältere Version von Druid durchführen können. Aus diesem Grund empfehlen wir dringend, zu bestätigen, dass Druid 0.16 in Ihrem Cluster stabil ist, bevor Sie diese Funktion aktivieren. Es hat einen bescheidenen Namen, aber die Änderungen der geringfügigen Verdichtung sind tiefgreifend, und es ist nicht möglich, die Mechanismen, die dies in diesen release notes antreiben, angemessen zu beschreiben, also schauen Sie sich den Vorschlag und die PR für weitere Details an. https://github.com/apache/incubator-druid/issues/7491 https://github.com/apache/incubator-druid/pull/7547

<a name="indexer" href="#indexer">#</a> Druid-"Indexer"-Prozess

Der neue Indexer-Prozess ist eine Alternative zum Aufgabenausführungssystem MiddleManager + Peon. Anstatt pro Aufgabe einen separaten JVM-Prozess zu forken, führt der Indexer Aufgaben als separate Threads innerhalb eines einzelnen JVM-Prozesses aus. Der Indexer ist im Vergleich zum MiddleManager + Peon-System einfacher zu konfigurieren und bereitzustellen und ermöglicht eine bessere gemeinsame Nutzung von Ressourcen zwischen Aufgaben. Der Vorteil des Indexers besteht darin, dass er die gemeinsame Nutzung von Abfrageverarbeitungsressourcen, Suchvorgängen, zwischengespeicherten Authentifizierungs-/Autorisierungsinformationen und vielem mehr zwischen allen laufenden Indizierungsaufgabenthreads ermöglicht, wodurch jede einzelne Aufgabe Zugriff auf einen größeren Ressourcenpool erhält und weitaus weniger redundante Aktionen ausgeführt werden, als dies mit dem Peon-Ausführungsmodell möglich ist, bei dem jede Aufgabe in ihrem eigenen Prozess isoliert ist. Die Verwendung von Indexer bringt jedoch einen Nachteil mit sich: Der Verlust der Prozessisolation durch Peon-Prozesse bedeutet, dass eine einzelne Aufgabe potenziell alle laufenden Indexierungsaufgaben auf diesem Indexer beeinträchtigen kann. Die Konfigurationen druid.worker.globalIngestionHeapLimitBytes und druid.worker.numConcurrentMerges sollen dazu beitragen, dies zu minimieren. Darüber hinaus werden Aufgabenprotokolle für Indexer-Prozesse in das Indexer-Prozessprotokoll integriert und nicht im Deep Storage gespeichert. Sie können mit der Indizierung beginnen, indem Sie beim Starten des Dienstes server indexer als Befehlszeilenargument für org.apache.druid.cli.Main angeben. Um Indexer anstelle von MiddleManager und Peon zu verwenden, sollten Sie in der Lage sein, Werte aus der Konfiguration in die Indexer-Konfiguration anzupassen, druid.indexer.fork.property.-Konfigurationen direkt auf den Indexer zu übertragen und Heap- und Direktspeicher basierend auf den Peon-Größen multipliziert mit der Anzahl der Aufgabenslots zu dimensionieren (im Gegensatz zu einem MiddleManager akzeptiert er die Konfigurationen druid.indexer.runner.javaOpts oder druid.indexer.runner.javaOptsArray nicht). Weitere Informationen finden Sie in der Indexer-Dokumentation. https://github.com/apache/incubator-druid/pull/8107

<a name="shuffle" href="#shuffle">#</a> Native parallele Batch-Indizierung mit Shuffle

In 0.16.0 unterstützt die native parallele Batch-Indizierungsaufgabe index_parallel von Druid jetzt ein „perfektes“ Rollup mit der Implementierung eines zweistufigen Shuffle-Prozesses. Aufgaben in Stufe 1 führen eine sekundäre Partitionierung von Zeilen zusätzlich zur standardmäßigen zeitbasierten Partitionierung der Segmentgranularität durch und erstellen ein Zwischendatensegment für jede Partition. Den Aufgaben der Stufe 2 wird jeweils ein Satz der in Stufe 1 erstellten Partitionierungen zugewiesen. Sie sammeln und kombinieren den Satz von Zwischendatensegmenten, die zu dieser Partitionierung gehören, sodass beim Erstellen der endgültigen Segmente ein vollständiges Rollup erreicht werden kann. Derzeit wird nur Hash-basierte Partitionierung unterstützt. Dies kann aktiviert werden, indem forceGuaranteedRollup in tuningConfig auf true gesetzt wird. numShards in partitionsSpec und intervals in granularitySpec müssen ebenfalls eingestellt werden. Die Druid MiddleManager-Prozesse (oder die neuen Indexer-Prozesse) haben eine neue Verantwortung für diese Indizierungsaufgaben und stellen die Ausgabe der Zwischenpartitionssegmente von Stufe 1 in die Aufgaben der Stufe 2 bereit. Je nach Konfiguration und Clustergröße muss daher die MiddleManager jvm-Konfiguration möglicherweise angepasst werden, um die Heap-Zuweisung und HTTP-Threads zu erhöhen. Es wird erwartet, dass diese Zahlen mit der Clustergröße skalieren, da alle an einem Shuffle beteiligten MiddleManager- oder Indexer-Prozesse die Fähigkeit benötigen, miteinander zu kommunizieren. Wir gehen jedoch nicht davon aus, dass der Platzbedarf wesentlich größer sein wird als derzeit. Optimistisch empfehlen wir, es mit Ihren vorhandenen Konfigurationen zu versuchen und die Heap- und HTTP-Thread-Anzahl nur dann zu erhöhen, wenn Probleme auftreten. https://github.com/apache/incubator-druid/issues/8061

<a name="sql-multi-value" href="#sql-multi-value">#</a> SQL- und native Ausdrucksunterstützung für mehrwertige Zeichenfolgenspalten

Druid SQL und native Abfrageausdrücke „virtuelle Spalten“ können nun korrekt mehrwertige String-Spalten verwenden, entweder als einzelne VARCHAR-Werte für Parität mit dem nativen Druid-Abfrageverhalten, oder als Array-ähnlicher Typ, mit einem neuen Satz mehrwertiger String-Funktionen. Beachten Sie, dass dies bisher nur in Abfragezeitausdrücken unterstützt wird; Die Verwendung mehrwertiger Ausdrücke zum Zeitpunkt der Aufnahme über einen transformSpec wird in einer zukünftigen Version verfügbar sein. Die vollständige Liste der hinzugefügten Funktionen und Verhaltensänderungen ist viel zu umfangreich, um sie hier aufzulisten. Weitere Informationen finden Sie in der Dokumentation zu SQL und expression. https://github.com/apache/incubator-druid/issues/7525 https://github.com/apache/incubator-druid/pull/7588 https://github.com/apache/incubator-druid/pull/7950 https://github.com/apache/incubator-druid/pull/7973 https://github.com/apache/incubator-druid/pull/7974 https://github.com/apache/incubator-druid/pull/8011

<a name="sql-timestampdiff" href="#sql-timestampdiff">#</a> TIMESTAMPDIFF

Als Ergänzung zu TIMESTAMPADD, das Zeitstempel nach Zeiteinheiten ändern kann, gibt es einen TIMESTAMPDIFF, der die vorzeichenbehaftete Anzahl von Zeiteinheiten zwischen zwei Zeitstempeln berechnen kann. Informationen zur Syntax finden Sie in der SQL-Dokumentation. https://github.com/apache/incubator-druid/pull/7695

<a name="sql-time-ceil" href="#sql-time-ceil">#</a> TIME_CEIL

TIME_CEIL, eine zeitspezifische, flexiblere Version der Funktion CEIL, wurde auch zu Druid 0.16.0 hinzugefügt. Diese Funktion kann einen Zeitstempel optional für eine bestimmte Zeitzone um einen ISO8601-Zeitraum aufrunden, z. B. P3M (Viertel) oder PT12H (halbe Tage). Weitere Informationen finden Sie in der SQL-Dokumentation. https://github.com/apache/incubator-druid/pull/8027

<a name="sql-ipv4" href="#sql-ipv4">#</a> IPv4

Druid 0.16.0 fügt außerdem spezielle SQL-Operatoren und native Ausdrücke für den Umgang mit IPv4-Internetadressen im Punkt-Dezimal-String- oder Integer-Format hinzu. Die neuen Operatoren sind IPV4_MATCH(address, subnet), IPV4_PARSE(address) und IPV4_STRINGIFY(address), die IP-Adressen Subnetzen in CIDR-Notation zuordnen, das Punkt-Dezimal-String-Format in das Ganzzahl-Format übersetzen bzw. das Ganzzahl-Format in das Punkt-Dezimal-String-Format übersetzen können. Weitere Informationen finden Sie in der SQL-Dokumentation. https://github.com/apache/incubator-druid/pull/8223

<a name="sql-nvl" href="#sql-nvl">#</a> NVL

Um die Freizügigkeit und SQL-Kompatibilität für Benutzer zu erhöhen, die mit Erfahrung in anderen Datenbanken zu Druid kommen, wurde ein Alias für die COALESCE-Funktion in der Form NVL hinzugefügt, den einige SQL-Dialekte stattdessen verwenden. Einzelheiten finden Sie in der SQL-Dokumentation https://github.com/apache/incubator-druid/pull/7965

<a name="string-sum" href="#string-sum">#</a> long/double/float sum/min/max Aggregator-Unterstützung für String-Spalten

<a name="docs" href="#docs">#</a> Aktualisierte Website-Dokumentation

Der Dokumentationsbereich der Druid-Website wurde umfassend aktualisiert und auf die Verwendung von Docusaurus umgestellt, wodurch viel schönere und funktionalere Seiten erstellt werden, als wir es derzeit haben. Jede Dokumentationsseite verfügt jetzt über ein ausklappbares Inhaltsverzeichnis auf der linken Seite, das den Überblick über die gesamten Dokumente zeigt, und über ein Inhaltsverzeichnis auf der rechten Seite, das den Überblick über die jeweilige Dokumentseite zeigt, was die Navigation erheblich verbessert. Darüber hinaus wurde die Aufnahmedokumentation vollständig aktualisiert, beginnend mit einem neuen ingestion/index.md-Dokument, das alle wichtigen Konzepte der Aufnahmespezifikationen vorstellt und die beliebtesten Aufnahmemethoden beschreibt. Dabei handelte es sich um eine dringend benötigte Überarbeitung vieler vorhandener Dokumentationsseiten, die im Laufe der Zeit organisch gewachsen waren und schwer verständlich geworden waren, in einen einfacheren Satz von weniger, größeren Seiten mit mehr Querverweisen. Sie sind auch etwas „meinungsbewusster“ und bringen neue Leute dazu, sich Kafka, Kinesis, Hadoop und nativer Batch-Ingestion zuzuwenden. Sie sprechen über Tranquility, stellen es aber nicht als etwas besonders Empfehlenswertes dar, da es sich tatsächlich im Minimalwartungsmodus befindet. Schauen Sie sich diese Verbesserungen (und viele weitere) hier an. https://github.com/apache/incubator-druid/pull/8311

Erweiterungen

<a name="dataasketches" href="#dataasketches">#</a> druid-dataasketches

Die druid-datasketches-Erweiterung, die auf Apache Dataasketches (Inkubation) aufbaut, wurde um drei neue Post-Aggregatoren erweitert: quantilesDoublesSketchToRank, der eine Annäherung an den Rang eines bestimmten Werts berechnet, der der Bruchteil der Verteilung kleiner als dieser Wert ist, und quantilesDoublesSketchToCDF, der eine Annäherung an die kumulative Verteilungsfunktion berechnet, wenn ein Array von Teilungspunkten gegeben ist, die die Kanten der Klassen definieren. Eine weitere Post-Aggregation, thetaSketchToString, die eine Zusammenfassung der Skizze druckt, wurde hinzugefügt, um das Debuggen zu unterstützen. Weitere Informationen finden Sie in der Datasketches-Erweiterungsdokumentation. https://github.com/apache/incubator-druid/pull/7550 https://github.com/apache/incubator-druid/pull/7937 Der HLLSketch-Aggregator wurde mit der Option round nur für die Abfragezeit verbessert, um das Runden von Werten in ganze Zahlen zu unterstützen und ihm Funktionsparität mit den integrierten Aggregatoren cardinality und hyperUnique zu verleihen. https://github.com/apache/incubator-druid/pull/8023 Schließlich sollten Benutzer von HllSketch auch eine Leistungsverbesserung aufgrund einiger vorgenommener Änderungen feststellen, die es Druid ermöglichen, eine leere Skizze vorab zu berechnen und diese in die Aggregationspuffer zu kopieren, wodurch die Zeit für die Initialisierung des Aggregators während der Abfrageverarbeitung erheblich verkürzt wird. https://github.com/apache/incubator-druid/pull/8194

<a name="stats" href="#stats">#</a> druid-stats

Die druid-stats-Kernerweiterung wurde um SQL-Unterstützung erweitert, wodurch VAR_POP und VAR_SAMP für die Berechnung der Varianzpopulation und -stichprobe mit dem Varianzaggregator sowie STDDEV_POP und STDDEV_SAMP für die Berechnung der Standardabweichungspopulation und -stichprobe mit dem Standardabweichungs-Postaggregator verfügbar gemacht werden. Darüber hinaus werden die Funktionen VARIANCE und STDDEV als Aliase für VAR_SAMP bzw. STDDEV_SAMP hinzugefügt. Weitere Einzelheiten finden Sie in der SQL-Dokumentation und in der Dokumentation zur Statistikerweiterung. https://github.com/apache/incubator-druid/pull/7801

<a name="histogram" href="#histogram">#</a> druid-histogram

Der „Fixed Bucket“-Histogramm-Aggregator der druid-histogram-Erweiterung verfügt über eine neu hinzugefügte Eigenschaft finalizeAsBase64Binary, die die Serialisierung des resultierenden Histogramms als Base64-Zeichenfolge anstelle einer für Menschen lesbaren JSON-Zusammenfassung ermöglicht, wodurch es mit dem ungefähren Histogramm-Aggregator derselben Erweiterung konsistent wird. Weitere Informationen finden Sie in der Dokumentation (https://druid.staged.apache.org/docs/latest/development/extensions-core/approximate-histograms.html#properties). https://github.com/apache/incubator-druid/pull/7784

<a name="statsd" href="#statsd">#</a> statsd-emitter

Die statsd-emitter-Erweiterung verfügt über eine neue Option, druid.emitter.statsd.dogstatsdServiceAsTag, die die Ausgabe des Druid-Dienstnamens als „Tag“ ermöglicht, z. B. druid_service:druid/broker anstelle eines Teils des Metriknamens wie in druid.broker.query.time. Als Präfix wird druid verwendet. Das Beispiel von druid.broker.query.time wäre also stattdessen druid.query.time, was Konsolidierungsmetriken über Druid-Diensttypen hinweg ermöglicht und stattdessen nach Tags unterscheidet. Damit diese Einstellung wirksam wird, muss druid.emitter.statsd.dogstatsd auf true gesetzt sein. Weitere Einzelheiten finden Sie in der Dokumentation (https://druid.staged.apache.org/docs/latest/development/extensions-contrib/statsd.html#configuration). https://github.com/apache/incubator-druid/pull/8238 https://github.com/apache/incubator-druid/pull/8472

<a name="tdigest" href="#tdigest">#</a> Neue Erweiterung: druid-tdigestsketch

In Druid 0.16 wurde ein neuer Satz ungefährer Skizzenaggregatoren zur Berechnung von Quantilen und dergleichen hinzugefügt, die auf t-digest basieren. T-Digest wurde für parallele Programmieranwendungsfälle wie verteilte Aggregationen oder Map-Reduction-Jobs entwickelt, indem es die Kombination zweier Zwischen-T-Digests einfach und effizient macht. Es dient zur Ergänzung bestehender Algorithmen, die von der Apache Dataasketches-Erweiterung und der Moments Sketch-Erweiterung bereitgestellt werden. Weitere Einzelheiten finden Sie in der Erweiterungsdokumentation. https://github.com/apache/incubator-druid/issues/7303 https://github.com/apache/incubator-druid/pull/7331

<a name="influxdb" href="#influxdb">#</a> Neue Erweiterung: druid-influxdb-emitter

In 0.16 wurde außerdem eine neue Druid-Emitter-Erweiterung hinzugefügt, die das Senden von Druid-Metriken an influxdb über HTTP ermöglicht. Derzeit sendet dieser Emitter nur Dienstmetrikereignisse an InfluxDB (eine Liste der Metriken finden Sie unter Druid-Metriken). Wenn ein Metrikereignis ausgelöst wird, wird es einer Ereigniswarteschlange hinzugefügt. Nach einer konfigurierbaren Zeitspanne werden die Ereignisse in der Warteschlange in das Zeilenprotokoll von InfluxDB umgewandelt und an den InfluxDB HTTP API gesendet. Zu diesem Zeitpunkt wird die gesamte Warteschlange geleert. Die Warteschlange wird auch geleert, wenn der Emitter heruntergefahren wird. Weitere Informationen finden Sie in den Erweiterungsdokumenten. https://github.com/apache/incubator-druid/pull/7717

<a name="tuning" href="#tuning">#</a> Feinabstimmung Ihrer Arbeitslasten

Neben der experimentellen vektorisierten Abfrage-Engine und dem neuen Indexer-Prozesstyp verfügt 0.16 auch über einige zusätzliche Funktionen, die eine potenzielle Feinabstimmung der Indizierung und Abfrageleistung durch Experimente ermöglichen.

<a name="intermediary-compression" href="#intermediary-compression">#</a> Steuerung der Indexierung der Zwischensegmentkomprimierung

Erstens die Möglichkeit, unabhängig zu steuern, welche Komprimierung verwendet wird (oder sie zu deaktivieren), wenn Zwischensegmente während der Indizierung beibehalten werden. Diese Konfiguration ist für die Eigenschaft indexSpec verfügbar und kann zu tuningConfig hinzugefügt werden als:

"indexSpecForIntermediatePersists": {
  "dimensionCompression": "uncompressed",
  "metricCompression": "none"
}

um beispielsweise die Komprimierung für Zwischensegmente vollständig zu deaktivieren. Ein möglicher Grund, „unkomprimierte“ Zwischensegmente in Betracht zu ziehen, besteht darin, die Menge an „direktem“ Java-Speicher einzusparen, die für die endgültige Zusammenführung von Zwischensegmenten erforderlich ist, bevor sie veröffentlicht und in den Deep Storage verschoben werden, da für das Lesen von Daten aus unkomprimierten Spalten nicht die 64-KB-Direktpuffer erforderlich sind, die zum Dekodieren von lz4 und anderen kodierten Spalten verwendet werden. Dies ist natürlich ein Kompromiss zwischen Speicherplatz und Seiten-Cache-Fußabdruck. Wir empfehlen daher, damit zu experimentieren, bevor Sie sich für eine Konfiguration entscheiden, die Sie für Ihre Produktions-Workloads verwenden möchten. https://github.com/apache/incubator-druid/pull/7919

<a name="filter-bitmaps" href="#filter-bitmaps">#</a> Filter-Bitmap-Indexnutzung steuern

Bitmap-Indizes stellen normalerweise eine enorme Leistungssteigerung für Druid dar, können jedoch in einigen Szenarien zu einer langsameren Abfragegeschwindigkeit führen, insbesondere bei rechenintensiven Filtern für Dimensionen mit sehr hoher Kardinalität. In Druid 0.16 ist jetzt ein neuer Mechanismus vorhanden, der eine gewisse manuelle Kontrolle darüber ermöglicht, wann Bitmap-Indizes verwendet werden und wann ein Filter als Zeilenscan ausgeführt wird, und der für jeden Filter und jede Abfrage verfügbar ist. Die meisten Filter akzeptieren eine neue Eigenschaft, filterTuning, die etwa so aussehen könnte:

"filterTuning": {
  "useBitmapIndex": true
}

Wenn useBitmapIndex auf „false“ gesetzt ist, kann ein Filter keine Bitmap-Indizes verwenden. Diese Eigenschaft ist optional und das Standardverhalten bleibt unverändert, wenn filterTuning nicht angegeben wird. Beachten Sie, dass diese Funktion nicht in der Benutzerdokumentation dokumentiert ist, als experimentell gilt und Änderungen in zukünftigen Versionen vorbehalten ist. https://github.com/apache/incubator-druid/pull/8209

<a name="request-logging" href="#request-logging">#</a> Protokollierung anfordern

Wenn Sie die Protokollierung von Druid-Anfragen gerne aktiviert hätten, aber Druid SQL verwenden und diese aufgrund der vielen Metadatenabfragen etwas zu gesprächig finden, haben Sie mit 0.16 Glück, denn es gibt eine neue Konfigurationsoption, die es ermöglicht, bestimmte Arten von Abfragen selektiv aus der Anforderungsprotokollierung auszublenden. Die Option druid.request.logging.mutedQueryTypes akzeptiert eine Liste von „queryType“-Zeichenfolgen, wie durch Druids native JSON-Abfrage API definiert, und verwendet standardmäßig eine leere Liste (damit nichts ignoriert wird). Zum Beispiel,

druid.request.logging.mutedQueryTypes=["segmentMetadata", "timeBoundary"]

würde alle Anforderungsprotokolle für segmentMetadata- und timeBoundary-Abfragen stummschalten. https://github.com/apache/incubator-druid/pull/7562

<a name="upgrading" href="#upgrading">#</a> Upgrade auf Druid 0.16.0

<a name="upgrading-s3" href="#upgrading-s3">#</a> S3-Aufgabenprotokollspeicher

Nach dem Upgrade auf 0.16.0 erfordern die Aufgabenprotokolle dieselben S3-Berechtigungen wie das Verschieben von Segmenten in den Deep Storage, was über eine zusätzliche Logik verfügt, um möglicherweise den Bucket-Eigentümer zu ermitteln (durch Abrufen der Bucket-ACL) und die ACL des Segmentobjekts festzulegen, um dem Bucket-Eigentümer vollen Zugriff zu gewähren. Wenn Sie die Bereitstellung dieser zusätzlichen Berechtigungen vermeiden möchten, kann das bestehende Verhalten durch die Einstellung druid.indexer.logs.disableAcl=true beibehalten werden. https://github.com/apache/incubator-druid/pull/7907

<a name="upgrading-sql" href="#upgrading-sql">#</a> Druid SQL

Druid SQL ist jetzt standardmäßig auf dem Router aktiviert. Beachten Sie, dass dies aufgrund zusätzlicher Metadatenabfragen, die zum Verwalten von Datenquellenschemata für die Abfrageplanung erforderlich sind, möglicherweise zusätzlichen Druck auf Brokerprozesse ausübt und durch die Einstellung druid.sql.enable=false deaktiviert werden kann, um das vorherige Verhalten beizubehalten. https://github.com/apache/incubator-druid/pull/7808

<a name="upgrading-lookup" href="#upgrading-lookup">#</a> Druid SQL-Suchfunktion

Druid-SQL-Abfragen, die die LOOKUP-Funktion verwenden, nutzen jetzt injective-Lookups, bei denen es sich um eine Eins-zu-eins-Transformation handelt, die die Durchführung einer Optimierung ermöglicht, die vermeidet, dass die Lookup-Auswertung auf historische Prozesse verlagert wird, und stattdessen ermöglicht, dass die Transformation später durchgeführt wird. Der Nachteil dieser Änderung besteht darin, dass Suchvorgänge, die fälschlicherweise als Eins-zu-eins-Transformation definiert sind, zum Zeitpunkt der Auswertung jedoch keine Eins-zu-eins-Transformation darstellen, zu falschen Abfrageergebnissen führen. https://github.com/apache/incubator-druid/pull/7655

<a name="upgrading-api" href="#upgrading-api">#</a> Koordinator-Metadaten API ändern sich

Die vom Koordinator bereitgestellten Metadaten API wurden geändert, um konsistentere HTTP-Antworten bereitzustellen. Die Änderungen sind geringfügig, aber nicht abwärtskompatibel, wenn Sie auf einen bestimmten API angewiesen sind.

  • POST /druid/coordinator/v1/datasources/{dataSourceName}
  • LÖSCHEN /druid/coordinator/v1/datasources/{dataSourceName}
  • POST /druid/coordinator/v1/datasources/{dataSourceName}/markUnused
  • POST /druid/coordinator/v1/datasources/{dataSourceName}/markUsed Geben Sie jetzt ein JSON-Objekt der Form {"numChangedSegments": N} anstelle von 204 (leere Antwort) zurück, wenn keine Segmente geändert wurden. Auf der anderen Seite Andererseits wird nicht 500 (Serverfehler) anstelle von 204 (leere Antwort) zurückgegeben.
  • POST /druid/coordinator/v1/datasources/{dataSourceName}/segments/{segmentId}
  • LÖSCHEN /druid/coordinator/v1/datasources/{dataSourceName}/segments/{segmentId} Geben Sie nun ein JSON-Objekt der Form {"segmentStateChanged": true/false} zurück. /druid/coordinator/v1/metadata/datasources?includeDisabled ist jetzt /druid/coordinator/v1/metadata/datasources?includeUnused. includeDisabled wird weiterhin akzeptiert, es wird jedoch eine Warnung in einem Protokoll ausgegeben. https://github.com/apache/incubator-druid/pull/7653

<a name="upgrading-compaction" href="#upgrading-compaction">#</a> Komprimierungsaufgaben

Die Option keepSegmentGranularity würde Komprimierungsaufgaben erstellen, die die Intervallgrenzen von Segmenten vor der Komprimierung ignorierten. Sie wurde jedoch nicht mehr unterstützt, da sie in den meisten Fällen nicht sehr nützlich war. Wenn Sie dieses Verhalten nützlich fanden, können Sie es dennoch erreichen, indem Sie segmentGranularity auf ALL setzen. https://github.com/apache/incubator-druid/pull/7747 Es gibt ein bekanntes Problem mit allen Druid-Versionen, die die automatische Komprimierung über den Koordinator unterstützen, wobei die automatische Komprimierung bei wiederholten Versuchen im gleichen Intervall hängen bleiben kann. Dieses Problem kann jetzt in 0.16 durch Festlegen von targetCompactionSizeBytes gemildert werden, ist jedoch weiterhin vorhanden, wenn maxRowsPerSegment oder maxTotalRows verwendet wird. Eine zukünftige Version von Druid wird dieses Problem vollständig beheben. https://github.com/apache/incubator-druid/issues/8481 https://github.com/apache/incubator-druid/pull/8495

<a name="upgrading-spec" href="#upgrading-spec">#</a> Indizierungsspezifikation

Alle nativen Indizierungsaufgabentypen verwenden jetzt PartitonsSpec, um die sekundäre Partitionierung so zu definieren, dass sie mit anderen Indizierungsaufgabentypen konsistent ist. Die Änderungen sind nicht abwärtsinkompatibel, aber Benutzer sollten eine Migration von maxRowsPerSegment, maxTotalRows, numShards und partitionDimensions auf die Partitionsspezifikation von nativen, Kafka- und Kinesis-Indizierungsaufgaben in Betracht ziehen. https://github.com/apache/incubator-druid/pull/8141

<a name="upgrading-kafka" href="#upgrading-kafka">#</a> Kafka-Indizierung

Die inkrementelle Veröffentlichung von Segmenten für den Indexierungsdienst Apache Kafka wurde in Druid 0.12 eingeführt. Zu diesem Zeitpunkt wurde der vorhandene Kafka-Indexierungsdienst als „Legacy“-Format beibehalten, um fortlaufende Updates von älteren Versionen von Druid zu ermöglichen. Diese „alte“ Codebasis wurde jetzt in Druid 0.16.0 entfernt, was bedeutet, dass ein fortlaufendes Update von einer älteren Druid-Version als 0.12.0 nicht unterstützt wird. https://github.com/apache/incubator-druid/pull/7735

<a name="upgrading-avro" href="#upgrading-avro">#</a> Avro-Erweiterung

Die Option fromPigAvroStorage wurde aus der Apache Avro-Erweiterung in Druid 0.16 entfernt, um Abhängigkeiten zu bereinigen. Diese Option stellte eine spezielle Transformation von GenericData.Array bereit, aber dieser Spaltentyp wird jetzt von der Standardimplementierung List verarbeitet. https://github.com/apache/incubator-druid/pull/7810

<a name="upgrading-kerberos" href="#upgrading-kerberos">#</a> Kerberos-Erweiterung

druid.auth.authenticator.kerberos.excludedPaths wird durch druid.auth.unsecuredPaths ersetzt, das für alle Authentifikatoren/Autorisierer gilt. Verwenden Sie daher stattdessen diese Konfigurationseigenschaft. https://github.com/apache/incubator-druid/pull/7745

<a name="upgrading-zk" href="#upgrading-zk">#</a> Zookeeper

Die Einstellung druid.zk.service.terminateDruidProcessOnConnectFail wurde entfernt und dies ist jetzt das Standardverhalten – Druid-Prozesse werden beendet, wenn eine nicht behandelte Curator client-Ausnahme auftritt, anstatt weiterhin im „Zombie“-Zustand zu laufen. Darüber hinaus steht jetzt eine neue optionale Einstellung druid.zk.service.connectionTimeoutMs zum Anpassen zur Verfügung, die mit der Einstellung Curator client connectionTimeoutMs verbunden ist. Standardmäßig wird weiterhin die Curator-Standardeinstellung 15000 Millisekunden verwendet. https://github.com/apache/incubator-druid/pull/8458

<a name="upgrading-realtime" href="#upgrading-realtime">#</a> Echtzeitprozess

Der veraltete eigenständige „Echtzeit“-Prozess wurde aus Druid entfernt. Von der Verwendung davon wurde seit einiger Zeit abgeraten, aber jetzt sollten middleManager und die neuen index-Prozesse alle Ihre Echtzeit-Indizierungsaufgaben verarbeiten. https://github.com/apache/incubator-druid/pull/7915 https://github.com/apache/incubator-druid/pull/8020
