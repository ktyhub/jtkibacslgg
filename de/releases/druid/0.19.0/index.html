Druide Druide-0.19.0

Apache Druid 0.19.0 enthält rund 200 neue Funktionen, Fehlerbehebungen, Leistungsverbesserungen, Dokumentationsverbesserungen und zusätzliche Testabdeckung von 51 Mitwirkenden. Weitere Einzelheiten finden Sie in der vollständigen Liste der Änderungen und alles, was mit dem Meilenstein markiert ist.

<a name="19-new-features" href="#19-new-features">#</a> Neue Funktionen

<a name="19-vectorize-default" href="#19-vectorize-default">#</a> Die vektorisierten Abfrage-Engines GroupBy und Timeseries sind standardmäßig aktiviert

[Vektorisierte Abfrage-Engines] (https://github.com/apache/druid/issues/7093) für GroupBy- und Timeseries-Abfragen wurden in Druid 0.16 als Opt-in-Funktion eingeführt. Seitdem haben wir diese Motoren ausgiebig getestet und sind der Meinung, dass es an der Zeit ist, diese Verbesserungen einem breiteren Publikum zugänglich zu machen. Beachten Sie, dass derzeit nicht die gesamte Abfrage-Engine vektorisiert ist. Diese Änderung sorgt jedoch dafür, dass jede Abfrage, die für die Vektorisierung geeignet ist, dies auch tut. Diese Funktion kann dennoch deaktiviert werden, wenn Probleme auftreten, indem Sie druid.query.vectorize auf false setzen. https://github.com/apache/druid/pull/10065

<a name="19-avro" href="#19-avro">#</a> Druid native Batch-Unterstützung für Apache Avro Object Container Files

Neu in Druid 0.19.0: Die native Batch-Indizierung unterstützt jetzt [Apache Avro Object Container Format] (https://avro.apache.org/docs/current/spec.html#Object+Container+Files) codierte Dateien und ermöglicht so die Batch-Aufnahme von Avro-Daten, ohne dass ein externer Hadoop-Cluster erforderlich ist. Weitere Informationen finden Sie in den Dokumenten (https://druid.apache.org/docs/0.19.0/ingestion/data-formats.html#avro-ocf). https://github.com/apache/druid/pull/9671

<a name="19-sql-input-source" href="#19-sql-input-source">#</a> Aktualisierte Druid-native Batch-Unterstützung für SQL-Datenbanken

In Druid 0.19.0 wurde eine „SqlInputSource“ hinzugefügt, um mit den neuen nativen Batch-Aufnahmespezifikationen zu arbeiten, die erstmals in Druid 0.17 eingeführt wurden, wodurch SqlFirehose veraltet ist. Wie „SqlFirehose“ unterstützt es derzeit MySQL und PostgreSQL und verwendet den Treiber dieser Erweiterungen. Hierbei handelt es sich um eine Aufnahmeaufgabe auf relativ niedrigem Niveau, und der Bediener muss manuell sicherstellen, dass die richtigen Daten aufgenommen werden, indem er entweder spezielle Abfragen erstellt, um sicherzustellen, dass keine doppelten Daten für Anhänge aufgenommen werden, oder indem er sicherstellt, dass beim Überschreiben der gesamte Datensatz abgefragt wird, um ihn zu ersetzen. Weitere Betriebsdetails finden Sie in den Dokumenten (https://druid.apache.org/docs/0.19.0/ingestion/native-batch.md#sql-input-source). https://github.com/apache/druid/pull/9449

<a name="19-ranger" href="#19-ranger">#</a> Apache Ranger-basierte Autorisierung

Eine neue Erweiterung in Druid 0.19.0 fügt einen Autorisierer hinzu, der die Zugriffskontrolle für Druid implementiert, unterstützt von Apache Ranger. Weitere Informationen zu den grundlegenden Funktionen, die diese Erweiterung bietet, finden Sie in der [Erweiterungsdokumentation]((https://druid.apache.org/docs/0.19.0/development/extensions-core/druid-ranger-security.html) und Authentifizierung und Autorisierung. https://github.com/apache/druid/pull/9579

<a name="19-aliyun-oss" href="#19-aliyun-oss">#</a> Alibaba Object Storage Service-Unterstützung

Für [Alibaba Cloud Object Storage Service (OSS)] (https://www.alibabacloud.com/product/oss) wurde eine neue „Contrib“-Erweiterung hinzugefügt, um sowohl Deep Storage als auch die Nutzung als Batch-Ingestion-Eingabequelle bereitzustellen. Da es sich um eine „Contrib“-Erweiterung handelt, wird sie nicht standardmäßig in die Binärdistribution gepackt. Weitere Informationen zur Verwendung in Ihrem Cluster finden Sie unter Community-Erweiterungen. https://github.com/apache/druid/pull/9898

<a name="19-gce-autoscale" href="#19-gce-autoscale">#</a> Automatische Skalierung des Aufnahme-Workers für Google Compute Engine

Eine weitere neue „Contrib“-Erweiterung in 0.19.0 wurde hinzugefügt, um die automatische Skalierung von Aufnahme-Workern zu unterstützen, die es einem Druiden-Overlord ermöglicht, Worker-Instanzen (MiddleManager oder Indexer) für Google Compute Engine bereitzustellen oder zu beenden, wenn ausstehende Aufgaben oder inaktive Worker vorhanden sind. Im Gegensatz zur Amazon Web Services-Ingestion-Autoscaling-Erweiterung, die Instanzen direkt bereitstellt und beendet, ohne eine Auto Scaling-Gruppe zu verwenden, verwendet der GCE-Autoscaler [Managed Instance Groups] (https://cloud.google.com/compute/docs/instance-groups#managed_instance_groups), um sich besser an die Art und Weise anzupassen, wie Betreiber ihre Cluster in GCE wahrscheinlich bereitstellen. Wie andere „Contrib“-Erweiterungen wird sie nicht standardmäßig in die Binärdistribution gepackt. Weitere Informationen zur Verwendung in Ihrem Cluster finden Sie unter Community-Erweiterungen. https://github.com/apache/druid/pull/8987

<a name="19-regexp-like" href="#19-regexp-like">#</a> REGEXP_LIKE

Druid SQL und nativen Ausdrücken wurde eine neue Funktion REGEXP_LIKE hinzugefügt, die sich ähnlich wie LIKE verhält, außer dass für das Muster reguläre Ausdrücke verwendet werden. https://github.com/apache/druid/pull/9893

<a name="19-web-lookup" href="#19-web-lookup">#</a> Verbesserungen bei der Suchverwaltung in der Webkonsole

Die Druid 0.19-Webkonsole enthält außerdem einige nützliche Verbesserungen an der Nachschlagetabellen-Verwaltungsschnittstelle. Das Erstellen und Bearbeiten von Lookups erfolgt jetzt über ein Formular zur Annahme von Benutzereingaben und nicht mehr über einen Rohtexteditor zur Eingabe der JSON-Spezifikation. <img width="682" alt="Screenshot 2020-04-02 um 1 14 38 Uhr" src="https://user-images.githubusercontent.com/37322608/78221645-fa2b5080-7480-11ea-9824-c74e121575f3.png"> Darüber hinaus ermöglicht das Klicken auf das Lupensymbol neben einem Lookup nun die Anzeige der ersten 5000 Werte dieses Lookups. <img width="1129" alt="Screenshot 20.03.2020 um 15 09 24 Uhr" src="https://user-images.githubusercontent.com/37322608/77206532-cd5c5e00-6abc-11ea-9ea0-0680fa5de8cb.png"> https://github.com/apache/druid/pull/9549 https://github.com/apache/druid/pull/9587

<a name="19-datasource-loadstatus" href="#19-datasource-loadstatus">#</a> Neuer Koordinator pro Datenquelle „loadstatus“ API

Ein Koordinator API kann es einfacher machen, festzustellen, ob die neuesten veröffentlichten Segmente für Abfragen verfügbar sind. Dies ähnelt dem vorhandenen Koordinator „loadstatus“ API, ist jedoch datenquellenspezifisch, kann ein Intervall angeben und kann optional den Metadatenspeicher-Snapshot live aktualisieren, um die neuesten Informationen zu erhalten. Beachten Sie, dass Bediener dennoch Vorsicht walten lassen sollten, wenn sie diesen API zum Abfragen einer großen Anzahl von Segmenten verwenden, insbesondere wenn sie eine Metadatenaktualisierung erzwingen, da es sich bei großen Clustern möglicherweise um einen „schweren“ Aufruf handeln kann. https://github.com/apache/druid/pull/9965

<a name="19-batch-append" href="#19-batch-append">#</a> Native Batch-Append-Unterstützung für Bereichs- und Hash-Partitionierung

Teilweise Fehlerbehebung, teils neue Funktion: Druid-nativer Batch unterstützt (erneut) das Anhängen neuer Daten an vorhandene Zeitblöcke, wenn diese Zeitblöcke mit „Hash“- oder „Range“-Partitionierungsalgorithmen partitioniert wurden. Beachten Sie, dass die angehängten Segmente derzeit nur „dynamische“ Partitionierung unterstützen und dass diese angehängten Segmente beim Zurücksetzen auf ältere Versionen nach dem Downgrade von Druid nicht erkannt werden. Um ein Rollback auf eine frühere Version durchzuführen, sollten diese angehängten Segmente mit dem restlichen Zeitblock komprimiert werden, um ein homogenes Partitionierungsschema zu erhalten. https://github.com/apache/druid/pull/10033

<a name="19-bugs" href="#19-bugs">#</a> Fehlerbehebungen

Druid 0.19.0 enthält 65 Fehlerbehebungen, die vollständige Liste finden Sie hier (https://github.com/apache/druid/pulls?q=is%3Apr+milestone%3A0.19.0+is%3Aclosed+label%3ABug).

<a name="19-partition-non-atomic" href="#19-partition-non-atomic">#</a> Korrektur für stapelweise aufgenommene „dynamische“ partitionierte Segmente, die nicht atomar abfragbar werden

Druid 0.19.0 behebt ein wichtiges Problem mit der Abfragekorrektheit, bei dem „dynamische“ partitionierte Segmente, die von einer Batch-Aufnahmeaufgabe erzeugt wurden, nicht die Gesamtzahl der Partitionen verfolgten. Dies hatte zur Folge, dass diese Segmente, wenn sie online gingen, nicht als vollständiger Satz, sondern als einzelne Segmente erfolgten, was bedeutet, dass es Phasen des Austauschs gab, in denen innerhalb eines Zeitblocks Ergebnisse von einem unvollständigen Partitionssatz abgefragt werden konnten. https://github.com/apache/druid/pull/10025

<a name="19-partition-empty-buckets" href="#19-partition-empty-buckets">#</a> Korrektur, um zu ermöglichen, dass „Hash“- und „Range“-partitionierte Segmente mit leeren Buckets jetzt abfragbar sind

Vor 0.19.0 hatte Druid einen Fehler bei der Verwendung von Hash oder Bereichspartitionierung, bei dem die Partitionen nie als „vollständig“ erkannt und daher nie abfragbar wurden, wenn die Datenverzerrung so groß war, dass einer der Buckets nach der Aufnahme „leer“ war. Druid 0.19.0 behebt dieses Problem, indem es das Schema der Partitionierungsspezifikation anpasst. Diese Änderungen am json-Format sollten abwärtskompatibel sein. Durch ein Zurücksetzen auf eine frühere Version sind diese Segmente jedoch wieder nicht mehr abfragbar. https://github.com/apache/druid/pull/10012

<a name="19-bad-balancer" href="#19-bad-balancer">#</a> Falsches Balancer-Verhalten

Ein Fehler in Druid-Versionen vor 0.19.0 ermöglichte einen (falschen) Koordinatorbetrieb für den Fall, dass druid.server.maxSize nicht festgelegt war. Dieser Fehler würde das Laden von Segmenten und deren zufälligen Ausgleich im Cluster ermöglichen (unabhängig davon, welche Balancer-Strategie tatsächlich konfiguriert wurde), wenn dieser Wert nicht für alle historischen Daten festgelegt wäre. Dieser Fehler wurde behoben, aber als Ergebnis muss druid.server.maxSize auf die Summe der Segment-Cache-Speicherortgrößen für historische Daten gesetzt werden, sonst werden keine Segmente geladen. https://github.com/apache/druid/pull/10070

<a name="19-upgrading-from- previous" href="#19-upgrading-from- previous">#</a> Upgrade auf Druid 0.19.0

Bitte beachten Sie die folgenden Probleme beim Upgrade von 0.18.1 auf 0.19.0. Wenn Sie von einer früheren Version als 0.18.1 aktualisieren, sehen Sie sich bitte die release notes der entsprechenden Zwischenversionen an.

<a name="19-server-size" href="#19-server-size">#</a> 'druid.server.maxSize' muss jetzt für historische Server festgelegt werden

Eine Koordinator-Fehlerbehebung erfordert als Nebeneffekt nun die Einstellung von druid.server.maxSize für das Laden von Segmenten. Während dieser Wert für frühere Versionen korrekt eingestellt sein sollte, stellen Sie bitte sicher, dass dieser Wert korrekt konfiguriert ist, bevor Sie Ihre Cluster aktualisieren, da sonst Segmente nicht geladen werden. https://github.com/apache/druid/pull/10070

<a name="19-sys-segments-payload" href="#19-sys-segments-payload">#</a> Die Spalte „Payload“ der Systemtabellen „sys.segments“ wurde entfernt und durch „Dimensionen“, „Metriken“ und „ShardSpec“ ersetzt.

Das Entfernen der Spalte „Payload“ aus der Tabelle sys.segments sollte Abfragen in dieser Tabelle wesentlich effizienter machen. Die nützlichsten Felder daraus, die Liste der „Dimensionen“, „Metriken“ und „ShardSpec“, wurden aufgeteilt und stehen daher weiterhin für die Verarbeitung von Abfragen zur Verfügung. https://github.com/apache/druid/pull/9883

<a name="19-segment-load-threads" href="#19-segment-load-threads">#</a> Die Standardanzahl der Segmentlade-Threads wurde geändert

Der Standardwert der druid.segmentCache.numLoadingThreads-Konfiguration wurde von „Anzahl der Kerne“ in „Anzahl der Kerne“ dividiert durch 6 geändert. Dadurch sollten sich die historischen Daten beim Laden einer großen Anzahl von Segmenten sofort etwas besser verhalten, wodurch die Auswirkungen auf die Abfrageleistung begrenzt werden. https://github.com/apache/druid/pull/9856

<a name="19-broadcast-colocated" href="#19-broadcast-colocated">#</a> Broadcast-Laderegeln verfügen nicht mehr über „colocated datasources“

Zu 0.19.0 wurden eine Reihe unvollständiger Änderungen hinzugefügt, um effizientere Join-Abfragen zu ermöglichen, die auf der Idee basieren, Broadcast-Laderegeln zu verwenden, um kleinere Datenquellen im Cluster zu verbreiten, sodass Join-Vorgänge auf die Verarbeitung einzelner Segmente verlagert werden können. Obwohl es sich noch nicht um eine fertige Funktion handelt, verfügen die „Broadcast“-Laderegeln im Rahmen der Änderungen, die dies ermöglichen, nicht mehr über das Konzept „kolokalisierter Datenquellen“, das versuchen würde, Segmente nur an Server zu senden, die über Segmente der konfigurierten Datenquelle verfügten. Dies funktionierte in der Praxis nicht so gut, da es nicht atomar war, was bedeutete, dass die Broadcast-Segmente hinter den Lasten und Drops der kolokalisierten Datenquelle zurückblieben, also beschlossen wir, es zu entfernen. https://github.com/apache/druid/pull/9971

<a name="19-broadcast-broker-load" href="#19-broadcast-broker-load">#</a> Broker und Echtzeitaufgaben können jetzt so konfiguriert werden, dass sie Segmente aus „Broadcast“-Datenquellen laden

Ein weiterer Effekt der oben genannten Vorarbeiten zur Einführung effizienter „Broadcast-Joins“: Broker und Echtzeit-Indizierungsaufgaben laden nun Segmente, die durch „Broadcast“-Regeln geladen werden, wenn ein Segment-Cache konfiguriert ist. Da die Funktion nicht vollständig ist, gibt es kaum einen Grund, dies in 0.19.0 zu tun, und es wird nicht passieren, es sei denn, es wird explizit konfiguriert. https://github.com/apache/druid/pull/9971

<a name="19-lpad-rpad" href="#19-lpad-rpad">#</a> Verhaltensänderung von lpad und rpad-Funktion

Die lpad- und rpad-Funktionen haben im Druids-Standardmodus, der nicht mit SQL kompatibel ist, eine leichte Verhaltensänderung erfahren, damit sie sich konsistent mit PostgreSQL verhalten. Wenn der Pad-Ausdruck im neuen Verhalten eine leere Zeichenfolge ist, besteht das Ergebnis aus den (möglicherweise gekürzten) Originalzeichen, anstatt dass die leere Zeichenfolge als Null behandelt wird und die Ergebnisse auf Null gezwungen werden. https://github.com/apache/druid/pull/10006

<a name="19-interfaces" href="#19-interfaces">#</a> Von Erweiterungen, die benutzerdefinierte Druid-Ausdrücke bereitstellen, wird nun erwartet, dass sie die Methoden equal und hashCode implementieren

Eine Änderung an der Expr-Schnittstelle in Druid 0.19.0 erfordert, dass jede Erweiterung, die benutzerdefinierte Ausdrücke über ExprMacroTable bereitstellt, auch die Methoden equals und hashCode implementieren muss, um ordnungsgemäß zu funktionieren, insbesondere bei JOIN-Abfragen, die auf Filter- und Ausdrucksanalysen angewiesen sind, um zu bestimmen, wie eine Abfrage optimal verarbeitet werden kann. https://github.com/apache/druid/pull/9830

<a name="19-known-issues" href="#19-known-issues">#</a> Bekannte Probleme

Eine vollständige Liste der offenen Probleme finden Sie unter https://github.com/apache/druid/labels/Bug.
