año v2.5.0

#Changelog

Nuevas características

  • Modos de ejecución en equipo: se introdujo la enumeración TeamMode con cuatro modos de ejecución:
    • coordinate (predeterminado): patrón de supervisor donde el líder elige miembros, elabora tareas y sintetiza respuestas.
    • route: Patrón de enrutador donde el líder dirige a un especialista y devuelve su respuesta directamente
    • broadcast: Patrón de transmisión donde el líder delega la misma tarea a todos los miembros simultáneamente
    • tasks: ejecución autónoma basada en tareas donde el líder descompone los objetivos en una lista de tareas compartida
  • Human-in-the-Loop (HITL) para equipos: sistema RunRequirement mejorado para ejecuciones en pausa con mejor soporte para:
    • Flujos de confirmación de herramientas.
    • Colección de entradas del usuario con validación de esquema.
    • Ejecución de herramientas externas.
  • Sistema de aprobación: Nuevo decorador @approval para flujos de trabajo de aprobación humana:
    • @approval(type="required"): Bloqueo de aprobación que pausa la ejecución hasta que se resuelva mediante aprobaciones API
    • @approval(type="audit"): pista de auditoría sin bloqueo para cumplimiento/registro
    • Registros de aprobación persistentes con seguimiento de estado (pendiente, aprobado, rechazado, vencido, cancelado)
    • Aprobaciones API para listar, inspeccionar y resolver aprobaciones
  • Programador: programación basada en cron para agentes, equipos y flujos de trabajo con soporte de reintento, tiempo de espera y zona horaria.
  • LearningMachine for Teams: se agregó soporte para LearningMachine para aprendizaje persistente.
  • Fábricas invocables para herramientas, conocimientos y miembros: las herramientas, el conocimiento y los miembros del equipo ahora se pueden definir como fábricas invocables que se resuelven en tiempo de ejecución con acceso a RunContext. Admite almacenamiento en caché a través de cache_callables y claves de caché personalizadas para resolución en el ámbito de la sesión.
  • Infra: Agrega soporte para AWS EFS
  • Aislamiento de conocimientos: se agregó isolate_vector_search flag a la clase de conocimientos. Cuando está habilitado, los documentos se etiquetan con metadatos linked_to durante la inserción y las búsquedas se filtran por esta etiqueta, lo que permite que varias instancias de conocimiento compartan la misma base de datos vectorial mientras se mantienen resultados de búsqueda aislados. El valor predeterminado es False para lograr compatibilidad con datos existentes.

Mejoras

  • Refactor de agente/equipo: importante refactor interno de las clases de agente y equipo para una separación más clara de las preocupaciones.

Corrección de errores:

  • LanceDb Cloud: Se corrigió search() para dejar de reabrir la mesa; utilice .to_list() en lugar de .to_pandas() en búsqueda vectorial/híbrida/por palabra clave.
  • Restricción de clave principal: Se corrigió la tabla sessions, component_configs y component_links para usar la clave principal en lugar de _unique_constraints.

Cambios importantes

  • store_history_messages ahora tiene como valor predeterminado False: los mensajes del historial ya no se almacenan de forma predeterminada. Esto reduce la sobrecarga innecesaria de almacenamiento, mejora la privacidad al no conservar el historial de conversaciones a menos que sea explícitamente necesario y brinda un mejor control sobre los costos de almacenamiento. Si confía en el historial almacenado, configure store_history_messages=True explícitamente.
  • Singularidad del conocimiento: las instancias de conocimiento ahora requieren una combinación única de base de datos, tabla y nombre de conocimiento. Varias instancias de conocimiento no pueden compartir la misma tabla sin nombres distintos para evitar conflictos de datos.
