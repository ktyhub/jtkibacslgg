druida druida-0.19.0

Apache Druid 0.19.0 contiene alrededor de 200 funciones nuevas, correcciones de errores, mejoras de rendimiento, mejoras de documentación y cobertura de pruebas adicionales de 51 contribuyentes. Consulte la lista completa de cambios y todo lo etiquetado en el hito para obtener más detalles.

<a name="19-new-features" href="#19-new-features">#</a> Nuevas funciones

<a name="19-vectorize-default" href="#19-vectorize-default">#</a> Motores de consultas vectorizadas GroupBy y Timeseries habilitados de forma predeterminada

Los motores de consulta vectorizados para consultas GroupBy y Timeseries se introdujeron en Druid 0.16, como una característica opcional. Desde entonces, hemos probado exhaustivamente estos motores y creemos que ha llegado el momento de que estas mejoras lleguen a un público más amplio. Tenga en cuenta que no todo el motor de consultas está vectorizado en este momento, pero este cambio hace que cualquier consulta que sea elegible para ser vectorizada lo haga. Es posible que esta función aún esté deshabilitada si encuentra algún problema al configurar druid.query.vectorize en false. https://github.com/apache/druid/pull/10065

<a name="19-avro" href="#19-avro">#</a> Soporte por lotes nativo de Druid para archivos contenedores de objetos Apache Avro

Como novedad en Druid 0.19.0, la indexación por lotes nativa ahora admite archivos codificados [Formato de contenedor de objetos Apache Avro] (https://avro.apache.org/docs/current/spec.html#Object+Container+Files), lo que permite la ingesta por lotes de datos de Avro sin necesidad de un clúster Hadoop externo. Consulte los documentos para obtener más detalles. https://github.com/apache/druid/pull/9671

<a name="19-sql-input-source" href="#19-sql-input-source">#</a> Soporte por lotes nativo de Druid actualizado para bases de datos SQL

Se agregó un 'SqlInputSource' en Druid 0.19.0 para trabajar con las nuevas especificaciones nativas de ingesta por lotes introducidas por primera vez en Druid 0.17, desaprobando SqlFirehose. Al igual que 'SqlFirehose', actualmente admite MySQL y PostgreSQL, utilizando el controlador de esas extensiones. Esta es una tarea de ingesta de nivel relativamente bajo, y el operador debe tener cuidado de garantizar manualmente que se ingieran los datos correctos, ya sea elaborando consultas especialmente para garantizar que no se ingieran datos duplicados para los anexos, o asegurándose de que se consulte todo el conjunto de datos para ser reemplazado al sobrescribir. Consulte [los documentos] (https://druid.apache.org/docs/0.19.0/ingestion/native-batch.md#sql-input-source) para obtener más detalles operativos. https://github.com/apache/druid/pull/9449

<a name="19-ranger" href="#19-ranger">#</a> Autorización basada en Apache Ranger

Una nueva extensión en Druid 0.19.0 agrega un Autorizador que implementa control de acceso para Druid, respaldado por Apache Ranger. Consulte [la documentación de la extensión]((https://druid.apache.org/docs/0.19.0/development/extensions-core/druid-ranger-security.html) y Autenticación y autorización para obtener más información sobre las funciones básicas que proporciona esta extensión. https://github.com/apache/druid/pull/9579

<a name="19-aliyun-oss" href="#19-aliyun-oss">#</a> Soporte del servicio de almacenamiento de objetos de Alibaba

Se agregó una nueva extensión 'contrib' para Alibaba Cloud Object Storage Service (OSS) para proporcionar almacenamiento profundo y uso como fuente de entrada de ingesta por lotes. Dado que se trata de una extensión 'contrib', no se empaquetará de forma predeterminada en la distribución binaria; consulte extensiones de la comunidad para obtener más detalles sobre cómo utilizarla en su clúster. https://github.com/apache/druid/pull/9898

<a name="19-gce-autoscale" href="#19-gce-autoscale">#</a> Escalado automático del trabajador de ingestión para Google Compute Engine

Se agregó otra extensión 'contrib' nueva en 0.19.0 para admitir el escalado automático de trabajadores de ingestión, que permite a Druid Overlord aprovisionar o finalizar instancias de trabajadores (MiddleManagers o Indexadores) siempre que haya tareas pendientes o trabajadores inactivos, para Google Compute Engine. A diferencia de la extensión de escalado automático de ingestión de Amazon Web Services, que aprovisiona y finaliza instancias directamente sin utilizar un grupo de Auto Scaling, el escalador automático de GCE utiliza Grupos de instancias administradas para alinearse más estrechamente con la forma en que los operadores probablemente aprovisionen sus clústeres en GCE. Al igual que otras extensiones 'contrib', no se empaquetará de forma predeterminada en la distribución binaria; consulte [extensiones de la comunidad] (https://druid.apache.org/docs/0.19.0/development/extensions.html#community-extensions) para obtener más detalles sobre cómo usarla en su clúster. https://github.com/apache/druid/pull/8987

<a name="19-regexp-like" href="#19-regexp-like">#</a> REGEXP_LIKE

Se ha agregado una nueva función REGEXP_LIKE a Druid SQL y a las expresiones nativas, que se comporta de manera similar a LIKE, excepto que usa expresiones regulares para el patrón. https://github.com/apache/druid/pull/9893

<a name="19-web-lookup" href="#19-web-lookup">#</a> Mejoras en la gestión de búsquedas de la consola web

La consola web Druid 0.19 también incluye algunas mejoras útiles en la interfaz de administración de tablas de búsqueda. La creación y edición de búsquedas ahora se realiza con un formulario para aceptar la entrada del usuario, en lugar de un editor de texto sin formato para ingresar la especificación JSON. <img width="682" alt="Captura de pantalla 2020-04-02 a las 1 14 38 a. m." src="https://user-images.githubusercontent.com/37322608/78221645-fa2b5080-7480-11ea-9824-c74e121575f3.png"> Además, cli hacer clic en el ícono de la lupa al lado de una búsqueda ahora permitirá mostrar los primeros 5000 valores de esa búsqueda. <img width="1129" alt="Captura de pantalla 2020-03-20 a las 3 09 24 PM" src="https://user-images.githubusercontent.com/37322608/77206532-cd5c5e00-6abc-11ea-9ea0-0680fa5de8cb.png"> https://github.com/apache/druid/pull/9549 https://github.com/apache/druid/pull/9587

<a name="19-datasource-loadstatus" href="#19-datasource-loadstatus">#</a> Nuevo coordinador por fuente de datos 'loadstatus' API

Un coordinador API puede facilitar la determinación de si los últimos segmentos publicados están disponibles para su consulta. Esto es similar al coordinador existente 'loadstatus' API, pero es específico de la fuente de datos, puede especificar un intervalo y, opcionalmente, puede actualizar en vivo la instantánea del almacén de metadatos para obtener la información más actualizada. Tenga en cuenta que los operadores aún deben tener cuidado al usar este API para consultar una gran cantidad de segmentos, especialmente si fuerzan una actualización de metadatos, ya que puede ser una llamada "pesada" en clústeres grandes. https://github.com/apache/druid/pull/9965

<a name="19-batch-append" href="#19-batch-append">#</a> Compatibilidad nativa con agregados por lotes para particiones de rango y hash

En parte corrección de errores, en parte característica nueva, el lote nativo de Druid (una vez más) admite agregar nuevos datos a fragmentos de tiempo existentes cuando esos fragmentos de tiempo se dividieron con algoritmos de partición 'hash' o 'rango'. Tenga en cuenta que actualmente los segmentos agregados solo admiten la partición "dinámica" y, al volver a versiones anteriores, Druid no reconocerá estos segmentos agregados después de la degradación. Para volver a una versión anterior, estos segmentos agregados deben compactarse con el resto del fragmento de tiempo para tener un esquema de partición homogéneo. https://github.com/apache/druid/pull/10033

<a name="19-bugs" href="#19-bugs">#</a> Corrección de errores

Druid 0.19.0 contiene 65 correcciones de errores, puedes ver [la lista completa aquí] (https://github.com/apache/druid/pulls?q=is%3Apr+milestone%3A0.19.0+is%3Aclosed+label%3ABug).

<a name="19-partition-non-atomic" href="#19-partition-non-atomic">#</a> Solución para segmentos particionados 'dinámicos' ingeridos por lotes que no se pueden consultar atómicamente

Druid 0.19.0 soluciona un problema importante de corrección de consultas, donde los segmentos particionados "dinámicos" producidos por una tarea de ingesta por lotes no rastreaban el número total de particiones. Esto implicaba que cuando estos segmentos se conectaban, no lo hacían como un conjunto completo, sino como segmentos individuales, lo que significaba que habría períodos de intercambio en los que se podrían consultar los resultados de un conjunto de particiones incompleto dentro de un período de tiempo. https://github.com/apache/druid/pull/10025

<a name="19-partition-empty-buckets" href="#19-partition-empty-buckets">#</a> Corrección para permitir que los segmentos particionados 'hash' y 'range' con depósitos vacíos ahora sean consultables

Antes de 0.19.0, Druid tenía un error al usar hash o particiones a distancia donde, si la desviación de los datos era tal que alguno de los depósitos estaba "vacío" después de la ingesta, las particiones nunca se reconocerían como "completas" y, por lo tanto, nunca serían consultables. Druid 0.19.0 soluciona este problema ajustando el esquema de la especificación de partición. Estos cambios en el formato json deberían ser compatibles con versiones anteriores; sin embargo, volver a una versión anterior hará que estos segmentos ya no sean consultables. https://github.com/apache/druid/pull/10012

<a name="19-bad-balancer" href="#19-bad-balancer">#</a> Comportamiento incorrecto del equilibrador

Un error en las versiones de Druid anteriores a 0.19.0 permitía la operación (incorrecta) del coordinador en caso de que druid.server.maxSize no estuviera configurado. Este error permitiría que los segmentos se cargaran y los equilibraran aleatoriamente de manera efectiva en el clúster (independientemente de qué estrategia de balanceador se haya configurado realmente) si todos los históricos no tuvieran este valor establecido. Este error se ha solucionado, pero como resultado, druid.server.maxSize debe configurarse en la suma de los tamaños de ubicación de caché de segmentos para los históricos; de lo contrario, no cargarán segmentos. https://github.com/apache/druid/pull/10070

<a name="19-upgrading-from-previous" href="#19-upgrading-from-previous">#</a> Actualizando a Druid 0.19.0

Tenga en cuenta los siguientes problemas al actualizar de 0.18.1 a 0.19.0. Si está actualizando desde una versión anterior a 0.18.1, consulte los release note de las versiones intermedias relevantes.

<a name="19-server-size" href="#19-server-size">#</a> 'druid.server.maxSize' ahora debe estar configurado para servidores históricos

Una corrección de error del Coordinador como efecto secundario ahora requiere que se configure druid.server.maxSize para que se carguen los segmentos. Si bien este valor debería haberse configurado correctamente para versiones anteriores, asegúrese de que esté configurado correctamente antes de actualizar sus clústeres; de lo contrario, no se cargarán los segmentos. https://github.com/apache/druid/pull/10070

<a name="19-sys-segments-payload" href="#19-sys-segments-payload">#</a> La columna 'carga útil' de las tablas del sistema 'sys.segments' se eliminó y se reemplazó con 'dimensiones', 'métricas' y 'shardSpec'

La eliminación de la columna "carga útil" de la tabla sys.segments debería hacer que las consultas en esta tabla sean mucho más eficientes, y los campos más útiles de esta, la lista de "dimensiones", "métricas" y "shardSpec", se han dividido y, por lo tanto, todavía están disponibles para dedicarlos al procesamiento de consultas. https://github.com/apache/druid/pull/9883

<a name="19-segment-load-threads" href="#19-segment-load-threads">#</a> Se cambió el número predeterminado de subprocesos de carga de segmentos

En la configuración de druid.segmentCache.numLoadingThreads se cambió el valor predeterminado de 'número de núcleos' a 'número de núcleos' dividido por 6. Esto debería hacer que los históricos se comporten un poco mejor desde el primer momento al cargar una gran cantidad de segmentos, lo que limita el impacto en el rendimiento de las consultas. https://github.com/apache/druid/pull/9856

<a name="19-broadcast-colocated" href="#19-broadcast-colocated">#</a> Las reglas de carga de transmisión ya no tienen 'fuentes de datos colocadas'

Se han agregado a 0.19.0 una serie de cambios incompletos para facilitar consultas de unión más eficientes, basados en la idea de utilizar reglas de carga de transmisión para propagar fuentes de datos más pequeñas entre el clúster para que las operaciones de unión puedan trasladarse al procesamiento de segmentos individuales. Si bien aún no es una característica terminada, como parte de los cambios para que esto suceda, las reglas de carga de "difusión" ya no tienen el concepto de "fuentes de datos colocadas", lo que intentaría transmitir solo segmentos a servidores que tuvieran segmentos de la fuente de datos configurada. Esto no funcionó tan bien en la práctica, ya que no era atómico, lo que significa que los segmentos de transmisión se quedarían atrás con respecto a cargas y caídas de la fuente de datos colocada, por lo que decidimos eliminarlo. https://github.com/apache/druid/pull/9971

<a name="19-broadcast-broker-load" href="#19-broadcast-broker-load">#</a> Ahora se pueden configurar corredores y tareas en tiempo real para cargar segmentos desde fuentes de datos de 'difusión'

Otro efecto del trabajo preliminar antes mencionado para introducir 'uniones de transmisión' eficientes. Los corredores y las tareas de indexación en tiempo real ahora cargarán segmentos cargados mediante reglas de 'difusión', si se configura un caché de segmentos. Dado que la función no está completa, hay pocas razones para hacer esto en 0.19.0 y no sucederá a menos que se configure explícitamente. https://github.com/apache/druid/pull/9971

<a name="19-lpad-rpad" href="#19-lpad-rpad">#</a> cambio de comportamiento de las funciones lpad y rpad

Las funciones lpad y rpad han pasado por un ligero cambio de comportamiento en el modo predeterminado no compatible con SQL de Druid, para que se comporten de manera consistente con PostgreSQL. En el nuevo comportamiento, si la expresión del pad es una cadena vacía, entonces el resultado serán los caracteres originales (posiblemente recortados), en lugar de que la cadena vacía se trate como nula y obligue a los resultados a ser nulos. https://github.com/apache/druid/pull/10006

<a name="19-interfaces" href="#19-interfaces">#</a> Ahora se espera que las extensiones que proporcionan expresiones Druidas personalizadas implementen métodos iguales y hashCode

Un cambio en la interfaz Expr en Druid 0.19.0 requiere que cualquier extensión que proporcione expresiones personalizadas a través de ExprMacroTable también debe implementar los métodos equals y hashCode para funcionar correctamente, especialmente con consultas JOIN, que se basan en filtros y análisis de expresiones para determinar cómo procesar una consulta de manera óptima. https://github.com/apache/druid/pull/9830
