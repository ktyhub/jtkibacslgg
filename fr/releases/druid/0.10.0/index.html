druid 0.10.0

Mineure Publié18 avr. 2017 Sourceapache/druid Anglais original

Cette page est traduite automatiquement. Le texte anglais original fait foi.

druide druide-0.10.0

Druid 0.10.0 contient des centaines d'améliorations de performances, d'améliorations de stabilité et de corrections de bugs provenant de plus de 40 contributeurs. Les nouvelles fonctionnalités majeures incluent une couche SQL intégrée, des dimensions numériques, la prise en charge de l'authentification Kerberos, une refonte de la tâche « index », un nouveau filtre « j'aime », de grandes colonnes, la possibilité d'exécuter le coordinateur et le suzerain en tant que service unique, des valeurs par défaut plus performantes et huit nouvelles extensions. Si vous effectuez une mise à niveau à partir d'une version précédente de Druid, veuillez consulter « Mise à jour à partir de 0.9.2 et versions antérieures » ci-dessous pour les notes de mise à niveau, y compris certaines modifications rétrocompatibles. La liste complète des changements est ici : https://github.com/druid-io/druid/pulls?utf8=%E2%9C%93&q=is%3Apr%20is%3Aclosed%20milestone%3A0.10.0 La documentation pour cette version se trouve à l'adresse suivante : http://druid.io/docs/0.10.0/

Faits saillants

SQL intégré

Druid inclut désormais un serveur SQL intégré alimenté par [Apache Calcite] (https://calcite.apache.org/). Druid fournit deux SQL API : HTTP POST et JDBC. Cela constitue une alternative au JSON API natif de Druid, plus familier aux nouveaux développeurs, et qui facilite l'intégration d'applications préexistantes parlant nativement SQL. Toutes les fonctionnalités Druid et SQL ne sont pas prises en charge par la couche SQL dans cette version initiale, mais nous avons l'intention de développer les deux dans les versions futures. La prise en charge de SQL peut être activée en définissant druid.sql.enable=true dans votre configuration. Voir http://druid.io/docs/0.10.0/querying/sql.html pour plus de détails et de documentation. Ajouté dans #3682 par @gianm.

Dimensions numériques

Druid prend désormais en charge les dimensions numériques au moment de l'ingestion et de la requête. Les utilisateurs peuvent ingérer des colonnes longues et flottantes en tant que dimensions (c'est-à-dire traiter les colonnes numériques comme faisant partie de la clé de regroupement au moment de l'ingestion plutôt que comme des agrégateurs, si le cumul est activé). De plus, les requêtes Druid peuvent désormais accepter n'importe quelle colonne longue ou flottante comme dimension de regroupement ou de filtrage. Il existe des compromis en termes de performances entre les colonnes de chaîne et les colonnes numériques. Les colonnes numériques sont généralement plus rapides à regrouper que les colonnes de chaînes. Les colonnes numériques n'ont pas d'index, elles sont donc généralement plus lentes à filtrer que les colonnes de chaînes. Voir http://druid.io/docs/0.10.0/ingestion/schema-design.html#numeric-dimensions pour la documentation sur l'ingestion et http://druid.io/docs/0.10.0/querying/dimensionspecs.html pour la documentation sur les requêtes. Ajouté dans #3838, #3966 et d'autres correctifs par @jon-wei.

Prise en charge de l'authentification Kerberos

Ajout d'une nouvelle extension nommée « druid-kerberos » qui ajoute la prise en charge de l'authentification utilisateur pour les nœuds Druid utilisant Kerberos. Il utilise le mécanisme de négociation simple et protégé GSSAPI, SPNEGO(https://en.wikipedia.org/wiki/SPNEGO) pour l'authentification via HTTP. Voir http://druid.io/docs/0.10.0/development/extensions-core/druid-kerberos.html pour obtenir de la documentation sur la configuration de l'authentification Kerberos. Ajouté dans #3853 par @nishantmonu51.

Refonte de la tâche d'indexation

La tâche d'indexation a été réécrite pour améliorer les performances, en particulier pour les tâches s'étalant sur plusieurs intervalles et générant de nombreux fragments. Le segmentGranularity intervals peut désormais être déterminé automatiquement et n'a plus besoin d'être spécifié, mais le temps d'ingestion peut être réduit si intervals et numShards sont fournis. De plus, la tâche d'indexation prend désormais en charge un indicateur appendToExisting qui entraîne l'indexation des données en tant que fragment supplémentaire de la version actuelle plutôt qu'en tant que nouvelle version éclipsant la version précédente. Voir http://druid.io/docs/0.10.0/ingestion/tasks.html#index-task pour la documentation. Ajouté dans #3611 par @dclim.

J'aime le filtre

Druid inclut désormais un filtre « J'aime » qui permet un filtrage de style SQL LIKE, tel que foo LIKE 'bar%'. La mise en œuvre est généralement plus rapide que les filtres regex et est encouragée par rapport aux filtres regex lorsque cela est possible. En particulier, les filtres similaires sur les préfixes tels que bar% sont nettement plus rapides que les filtres regex équivalents tels que ^bar.*. Voir http://druid.io/docs/0.10.0/querying/filters.html#like-filter pour la documentation. Ajouté dans #3642 par @gianm.

Grandes colonnes

Druid prend désormais en charge les colonnes individuelles de plus de 2 Go. Cette fonctionnalité n'est généralement pas requise, car d'une manière générale, les segments doivent généralement avoir une taille comprise entre 500 Mo et 1 Go, mais elle est utile dans les situations où une colonne est beaucoup plus grande que toutes les autres (par exemple, de grands croquis). Cette fonctionnalité est disponible pour tous les utilisateurs de Druid et aucune configuration particulière n'est nécessaire lors de l'utilisation des types de colonnes intégrés. Si vous avez développé un type de colonne de métrique personnalisé en tant qu'extension Druid, vous pouvez activer la prise en charge des grandes colonnes en remplaçant getSerializer dans votre ComplexMetricsSerde. Ajouté dans #3743 par @akashdw.

Option de combinaison Coordinateur/Overlord

Les déploiements de Druides peuvent désormais être simplifiés en combinant les fonctions Coordinateur et Overlord dans le processus Coordinateur. Pour ce faire, définissez druid.coordinator.asOverlord.enabled et druid.coordinator.asOverlord.overlordService de manière appropriée sur vos coordinateurs, puis arrêtez vos Overlords. La console Overlord serait disponible sur http://coordinator-host:port/console.html. Il s'agit actuellement d'une fonctionnalité expérimentale et désactivée par défaut. Nous avons l'intention d'envisager d'en faire la valeur par défaut dans une future version de Druid. Voir http://druid.io/docs/0.10.0/configuration/coordinator.html pour la documentation sur cette fonctionnalité et les options de configuration. Ajouté dans #3711 par @himanshug.

Valeurs par défaut plus performantes

Cette version modifie deux paramètres par défaut pour améliorer les performances prêtes à l'emploi :

  • L'option buildV9Directly introduite dans Druid 0.9.0 est désormais activée par défaut. Cette option améliore les performances d'indexation en créant directement le format de données v9 plutôt que de créer d'abord le format v8 puis de le convertir en v9. Si nécessaire, vous pouvez revenir à l'ancien code en définissant « buildV9Directly » sur false dans vos tâches d'indexation.
  • Le moteur groupBy v2 introduit dans Druid 0.9.2 est désormais activé par défaut. Ce nouveau moteur groupBy a été entièrement réécrit pour de meilleures performances et une meilleure gestion de la mémoire. Si nécessaire, vous pouvez revenir à l'ancien moteur en définissant soit "druid.groupBy.query.defaultStrategy" dans votre runtime.properties, soit "groupByStrategy" dans votre contexte de requête, sur "v1". Voir http://druid.io/docs/0.10.0/querying/groupbyquery.html pour plus de détails sur les différences entre groupBy v1 et v2.

Autres améliorations des performances

En plus de paramètres par défaut plus performants, le Druid 0.10.0 présente un certain nombre d'autres améliorations de performances, notamment :

  • Optimisation concise d'union, d'intersection et d'itération de bitset (#3883) par @leventov
  • Optimisation de la correspondance de valeurs basée sur DimensionSelector (#3858) par @leventov
  • Stratégie de requête de recherche pour choisir l'exécution basée sur l'index ou basée sur le curseur (#3792) par @jihoonson
  • Optimisation des itérations Bitset (#3753) par @leventov
  • Optimisation GroupBy pour la granularité "all" (#3740) par @gianm
  • Désactivez le vidage après chaque écriture de DefaultObjectMapper (#3748) par @jon-wei
  • Filtre ET court-circuit (#3676) par @gianm
  • Amélioration des performances d'IndexMergerV9 (#3440) par @leventov

Le processus de mise à jour standard de Druid décrit par http://druid.io/docs/0.10.0/operations/rolling-updates.html doit être suivi pour les mises à jour progressives.

Interroger les modifications de API

Veuillez noter les modifications suivantes de la requête rétrocompatible API lors de la mise à jour. Certaines requêtes devront peut-être être ajustées pour continuer à se comporter comme prévu.

  • Les fonctionnalités de requête JavaScript sont désormais désactivées par défaut pour des raisons de sécurité (#3818). Si vous utilisez ces fonctionnalités, vous pouvez les réactiver en définissant druid.javascript.enabled=true dans vos propriétés d'exécution. Voir http://druid.io/docs/0.10.0/development/javascript.html pour plus de détails, y compris les considérations de sécurité.
  • Les requêtes GroupBy n'autorisent plus __time comme nom de sortie d'une dimension, d'un agrégateur ou d'un post-agrégateur (#3967).
  • Sélectionnez les spécifications de pagination de requête par défaut sur le comportement fromNext: true lorsque fromNext n'est pas spécifié (#3986). Le comportement est inchangé pour les requêtes Select pour lesquelles fromNext est spécifié. Si vous préférez l'ancienne valeur par défaut, vous pouvez la modifier via la propriété d'exécution druid.query.select.enableFromNextDefault. Voir http://druid.io/docs/0.10.0/querying/select-query.html pour plus de détails.
  • Les requêtes SegmentMetadata n'incluent plus l'analyse "taille" par défaut (#3773). Vous pouvez toujours demander une analyse « taille » en ajoutant « taille » à « analysisTypes » au moment de la requête.

Modifications du déploiement et de la configuration

Veuillez noter les modifications suivantes liées au déploiement lors de la mise à jour.

  • Druid nécessite désormais Java 8 pour fonctionner (#3914). Si vous utilisez actuellement Java 7, nous vous suggérons de mettre à niveau Java d'abord, puis Druid.
  • Druid utilise désormais par défaut le moteur "v2" pour groupBy plutôt que l'ancien moteur "v1". Dans ce cadre, les limites d'utilisation de la mémoire sont passées de limites basées sur les lignes à celles basées sur les octets, il est donc possible que certaines requêtes qui respectaient auparavant les limites de ressources les dépassent et échouent. Vous pouvez éviter cela en réglant le nouveau moteur groupBy de manière appropriée. Si nécessaire, vous pouvez revenir à l'ancien moteur en définissant soit "druid.groupBy.query.defaultStrategy" dans votre runtime.properties, soit "groupByStrategy" dans votre contexte de requête, sur "v1". Voir http://druid.io/docs/0.10.0/querying/groupbyquery.html pour plus de détails sur les différences entre groupBy v1 et v2.<p>Ce nouveau moteur groupBy a été entièrement réécrit pour de meilleures performances et une meilleure gestion de la mémoire. La requête API et les résultats sont compatibles entre les deux moteurs ; cependant, il existe quelques différences du point de vue de la configuration du cluster : (1) groupBy v2 utilise principalement la mémoire hors tas au lieu de la mémoire sur tas ; (2) il nécessite un tampon de fusion pour chaque requête simultanée ; (3) si vous avez configuré la mise en cache pour groupBy, elle doit être sur les historiques ; et (4) il ne prend pas en charge chunkPeriod.
  • Druid a désormais une valeur par défaut non nulle pour druid.processing.numMergeBuffers (#3953). Cela augmentera la quantité de mémoire directe utilisée dans sa configuration par défaut. Cette modification a été effectuée dans le cadre du changement du moteur groupBy par défaut, puisque le nouveau moteur "v2" nécessite des tampons de fusion. Si vous utilisiez auparavant groupBy v1, vous devriez pouvoir compenser cela en réduisant votre tas JVM, car groupBy v2 utilise la mémoire hors tas plutôt que la mémoire sur tas.
  • Les processus liés aux requêtes Druid (tâches de courtage, d'historique et d'indexation) allouent désormais avec impatience le nombre druid.processing.numThreads d'instances DirectByteBuffer de taille druid.processing.buffer.sizeBytes pour le traitement des requêtes au démarrage (#3628). Cette allocation était paresseuse dans les versions antérieures de Druid. Ce changement n'affecte pas l'utilisation de la mémoire d'un cluster Druid de longue durée, mais cela signifie que la mémoire pour le traitement des tampons doit être disponible au démarrage de Druid.
  • Lors de l'exécution dans des fuseaux horaires non UTC, le comportement des constantes segmentGranularity prédéfinies telles que "jour" changera lors de la mise à niveau. Auparavant, cela générait des segments utilisant les jours locaux. Dans Druid 0.10.0, cela générera des segments en utilisant les jours UTC. Si vous exécutiez Druid dans le fuseau horaire UTC, cette modification n’a aucun effet. Veuillez noter que l'exécution de Druid dans un fuseau horaire non UTC n'est pas officiellement prise en charge (voir http://druid.io/docs/0.10.0/configuration/index.html) et nous vous recommandons de toujours exécuter tous les processus dans les fuseaux horaires UTC. Pour créer des segments de jour local à l'aide de Druid 0.10.0, vous pouvez utiliser une granularité de segment d'heure locale telle que :
"segmentGranularity" : {
     "type" : "period",
     "period" : "P1D",
     "timeZone" : "America/Los_Angeles"
}

Modifications des extensions

  • Les interfaces AggregatorFactory, BufferAggregator et PostAggregator ont changé (#3894, #3899, #3957, #4071). Si vous avez déployé une extension personnalisée qui inclut un AggregatorFactory ou PostAggregator, elle devra être recompilée. Les extensions intégrées de Druid ont toutes été mises à jour pour ce changement.
  • Les extensions ciblant Druid 0.10.x doivent être compilées avec JDK 8.
