druid 0.10.0

マイナー 公開日2017年4月18日 出典apache/druid 英語原文

このページは機械翻訳です。内容は必ず英文原文をご確認ください。

#ドルイドドルイド-0.10.0 Druid 0.10.0 には、40 人以上の寄稿者による何百ものパフォーマンスの改善、安定性の改善、バグ修正が含まれています。主な新機能には、組み込みの SQL レイヤー、数値ディメンション、Kerberos 認証のサポート、「インデックス」タスクの刷新、新しい「いいね」フィルター、大きな列、コーディネーターとオーバーロードを単一のサービスとして実行する機能、パフォーマンスの向上したデフォルト、および 8 つの新しい拡張機能が含まれます。 Druid の以前のバージョンからアップグレードする場合は、下位互換性のない変更を含むアップグレードに関する注意事項については、以下の「0.9.2 以前からのアップグレード」を参照してください。 変更点の完全なリストはここにあります: https://github.com/druid-io/druid/pulls?utf8=%E2%9C%93&q=is%3Apr%20is%3Aclosed%20milestone%3A0.10.0 このリリースのドキュメントは、http://druid.io/docs/0.10.0/ にあります。

ハイライト

組み込み SQL

Druid には、Apache Calcite を利用した組み込み SQL サーバーが含まれるようになりました。 Druid は、HTTP POST と JDBC という 2 つの SQL API を提供します。これにより、Druid のネイティブ JSON API の代替が提供され、新しい開発者にとってより馴染みがあり、SQL をネイティブに話す既存のアプリケーションを簡単に統合できます。この初期リリースでは、すべての Druid 機能と SQL 機能が SQL レイヤーでサポートされているわけではありませんが、将来のリリースでは両方を拡張する予定です。 SQL サポートは、構成で druid.sql.enable=true を設定することで有効にできます。詳細とドキュメントについては、http://druid.io/docs/0.10.0/querying/sql.html を参照してください。 @gianm によって #3682 に追加されました。

数値次元

Druid は、取り込み時とクエリ時に数値ディメンションをサポートするようになりました。ユーザーは、long 列と float 列をディメンションとして取り込むことができます (つまり、ロールアップが有効な場合、数値列を集計ではなく取り込み時のグループ化キーの一部として扱います)。さらに、Druid クエリは、グループ化またはフィルタリングのディメンションとして任意の長い列または浮動小数点列を受け入れることができるようになりました。 文字列列と数値列の間にはパフォーマンスのトレードオフがあります。一般に、数値列は文字列列よりもグループ化が速くなります。数値列にはインデックスがないため、一般に文字列列よりもフィルター処理が遅くなります。 インジェストのドキュメントについては http://druid.io/docs/0.10.0/ingestion/schema-design.html#numeric-dimensions を、クエリのドキュメントについては http://druid.io/docs/0.10.0/querying/dimensionspecs.html を参照してください。 @jon-wei によって #3838、#3966、およびその他のパッチに追加されました。

Kerberos 認証のサポート

「druid-kerberos」という名前の新しい拡張機能が追加されました。これは、Kerberos を使用した Druid ノードのユーザー認証のサポートを追加します。 HTTP 経由の認証には、シンプルで保護された GSSAPI ネゴシエーション メカニズム SPNEGO(https://en.wikipedia.org/wiki/SPNEGO) が使用されます。 Kerberos 認証の構成方法に関するドキュメントについては、http://druid.io/docs/0.10.0/development/extensions-core/druid-kerberos.html を参照してください。 @nishantmonu51 によって #3853 に追加されました。

インデックスタスクの刷新

インデックス作成タスクは、特に多数のシャードを生成する複数の間隔にわたるジョブのパフォーマンスを向上させるために書き直されました。セグメント粒度 intervals が自動的に決定されるようになり、指定する必要がなくなりましたが、intervals と numShards の両方を指定すると、取り込み時間を短縮できます。 さらに、インデックス作成タスクは、以前のバージョンを覆い隠す新しいバージョンとしてではなく、現在のバージョンの追加シャードとしてデータのインデックスを作成する appendToExisting フラグをサポートするようになりました。 ドキュメントについては、http://druid.io/docs/0.10.0/ingestion/tasks.html#index-task を参照してください。 @dclim によって #3611 に追加されました。

いいねフィルター

Druid には、foo LIKE 'bar%' などの SQL LIKE スタイルのフィルタリングを可能にする「like」フィルタが含まれるようになりました。通常、この実装は正規表現フィルターよりも高速であり、可能な場合は正規表現フィルターよりも実装することをお勧めします。特に、bar% などのプレフィックスに対する類似フィルターは、^bar.* などの同等の正規表現フィルターよりも大幅に高速です。 ドキュメントについては、http://druid.io/docs/0.10.0/querying/filters.html#like-filter を参照してください。 @gianm によって #3642 に追加されました。

大きな列

Druid は、2GB を超える個々の列をサポートするようになりました。一般的なガイダンスではセグメントのサイズは 500MB ～ 1GB であるべきであるため、この機能は通常は必要ありませんが、1 つの列が他のすべての列よりもはるかに大きい状況 (たとえば、大きなスケッチ) では便利です。 この機能はすべての Druid ユーザーが利用でき、組み込みの列タイプを使用する場合は特別な設定は必要ありません。 Druid 拡張機能としてカスタム メトリック列タイプを開発した場合は、ComplexMetricsSerde の getSerializer をオーバーライドすることで、大規模な列のサポートを有効にすることができます。 @akashdw によって #3743 に追加されました。

コーディネーター/オーバーロードの組み合わせオプション

コーディネーターとオーバーロードの機能をコーディネーター プロセスに組み合わせることで、ドルイドのデプロイメントを簡素化できるようになりました。これを行うには、コーディネーターで druid.coordinator.asOverlord.enabled と druid.coordinator.asOverlord.overlordService を適切に設定し、オーバーロードを停止します。 Overlord コンソールは http://coordinator-host:port/console.html で利用可能になります。 これは現在実験的な機能であり、デフォルトではオフになっています。 Druid の将来のバージョンでは、これをデフォルトにすることを検討する予定です。 この機能と構成オプションのドキュメントについては、http://druid.io/docs/0.10.0/configuration/coordinator.html を参照してください。 @himanshug によって #3711 に追加されました。

デフォルトのパフォーマンスが向上

このリリースでは、すぐに使えるパフォーマンスを向上させるために 2 つのデフォルト設定が変更されています。

  • Druid 0.9.0 で導入された buildV9Directly オプションがデフォルトで有効になりました。このオプションでは、最初に v8 を作成してから v9 に変換するのではなく、v9 データ形式を直接作成することにより、インデックス作成のパフォーマンスが向上します。必要に応じて、インデックス作成タスクで「buildV9Directly」を false に設定することで、古いコードにロールバックできます。
  • Druid 0.9.2 で導入された v2 groupBy エンジンがデフォルトで有効になりました。この新しい groupBy エンジンは、パフォーマンスとメモリ管理を向上させるために根本から書き直されました。必要に応じて、runtime.properties の「druid.groupBy.query.defaultStrategy」またはクエリ コンテキストの「groupByStrategy」のいずれかを「v1」に設定することで、古いエンジンにロールバックできます。 groupBy v1 と v2 の違いの詳細については、「http://druid.io/docs/0.10.0/querying/groupbyquery.html」を参照してください。

0.9.2 以前からのアップデート

アップグレード前に知っておくべき 0.9.2 と 0.10.0 の間の変更点については、以下を参照してください。 0.9.2 よりも前のバージョンから更新する場合は、関連する中間バージョンの release note で追加の注意事項を参照してください。

ローリングアップデート

ローリング アップデートでは、http://druid.io/docs/0.10.0/operations/rolling-updates.html で説明されている標準の Druid アップデート プロセスに従う必要があります。

API の変更をクエリする

更新時には、以下の下位互換性のないクエリ API が変更されることに注意してください。一部のクエリは、期待どおりに動作し続けるために調整が必要な場合があります。

  • JavaScript クエリ機能は、セキュリティ上の理由からデフォルトで無効になりました (#3818)。これらの機能を使用する場合は、ランタイム プロパティで druid.javascript.enabled=true を設定することで、再度有効にすることができます。セキュリティに関する考慮事項などの詳細については、http://druid.io/docs/0.10.0/development/javascript.html を参照してください。
  • GroupBy クエリでは、ディメンション、アグリゲーター、またはポストアグリゲーターの出力名として __time を使用できなくなりました (#3967)。
  • fromNext が指定されていない場合、選択クエリの pagingSpecs はデフォルトで fromNext: true 動作になるようになりました (#3986)。 fromNext が指定された選択クエリの動作は変わりません。古いデフォルトを使用したい場合は、druid.query.select.enableFromNextDefault ランタイム プロパティを通じてこれを変更できます。 詳細については、http://druid.io/docs/0.10.0/querying/select-query.html を参照してください。
  • SegmentMetadata クエリにはデフォルトで「サイズ」分析が含まれなくなりました (#3773)。クエリ時に「analysisTypes」に「size」を追加することで、「size」分析をリクエストすることもできます。

導入と構成の変更

更新する場合は、次の展開関連の変更点に注意してください。

  • Druid を実行するには Java 8 が必要になりました (#3914)。現在 Java 7 を実行している場合は、まず Java をアップグレードし、次に Druid をアップグレードすることをお勧めします。
  • Druid は、従来の「v1」エンジンではなく、groupBy の「v2」エンジンをデフォルトで使用するようになりました。 この一環として、メモリ使用量の制限が行ベースからバイトベースの制限に変更されたため、以前はリソース制限に達していた一部のクエリが制限を超えて失敗する可能性があります。 新しい groupBy エンジンを適切に調整することで、これを回避できます。必要に応じて、runtime.properties の「druid.groupBy.query.defaultStrategy」またはクエリ コンテキストの「groupByStrategy」のいずれかを「v1」に設定することで、古いエンジンにロールバックできます。 groupBy v1 と v2 の違いの詳細については、http://druid.io/docs/0.10.0/querying/groupbyquery.html を参照してください。<p>この新しい groupBy エンジンは、パフォーマンスとメモリ管理を向上させるために根本から書き直されました。クエリ API と結果は 2 つのエンジン間で互換性があります。ただし、クラスタ構成の観点からはいくつかの違いがあります。(1) groupBy v2 はオンヒープ メモリではなく主にオフヒープ メモリを使用します。 (2) 同時クエリごとに 1 つのマージ バッファが必要です。 (3) groupBy のキャッシュを構成した場合、それは履歴上にある必要があります。 (4) chunkPeriod をサポートしていません。
  • Druid の druid.processing.numMergeBuffers のデフォルト値がゼロ以外になりました (#3953)。これにより、デフォルト構成で使用されるダイレクト メモリの量が増加します。新しい「v2」エンジンにはマージ バッファが必要なため、この変更はデフォルトの groupBy エンジンの変更に関連して行われました。以前に groupBy v1 を使用していた場合、groupBy v2 はオンヒープ メモリではなくオフヒープ メモリを使用するため、JVM ヒープを減らすことでこれを相殺できるはずです。
  • Druid クエリ関連プロセス (ブローカー、ヒストリカル、インデックス作成タスク) は、起動時のクエリ処理のために、サイズ druid.processing.buffer.sizeBytes の DirectByteBuffer インスタンスの druid.processing.numThreads 数を積極的に割り当てるようになりました (#3628)。 Druid の以前のバージョンでは、この割り当ては遅延していました。この変更は、長時間実行されている Druid クラスターのメモリ使用には影響しませんが、Druid の起動時にバッファを処理するためのメモリが使用可能である必要があることを意味します。
  • UTC 以外のタイムゾーンで実行している場合、「日」などの事前定義されたセグメント粒度定数の動作がアップグレード時に変更されます。以前は、これにより現地の日を使用してセグメントが生成されていました。 Druid 0.10.0 では、UTC 日を使用してセグメントが生成されます。 UTC タイムゾーンで Druid を実行していた場合、この変更は効果がありません。 UTC 以外のタイムゾーンでの Druid の実行は公式にはサポートされていないことに注意してください (http://druid.io/docs/0.10.0/configuration/index.html を参照)。すべてのプロセスを常に UTC タイムゾーンで実行することをお勧めします。 Druid 0.10.0 を使用して現地日セグメントを作成するには、次のような現地時間セグメント粒度を使用できます。
"segmentGranularity" : {
     "type" : "period",
     "period" : "P1D",
     "timeZone" : "America/Los_Angeles"
}

拡張子の変更

  • AggregatorFactory、BufferAggregator、および PostAggregator インターフェイスが変更されました (#3894、#3899、#3957、#4071)。 AggregatorFactory または PostAggregator を含むカスタム拡張機能をデプロイした場合は、再コンパイルする必要があります。 Druid の組み込み拡張機能はすべて、この変更に合わせて更新されました。
  • Druid 0.10.x をターゲットとする拡張機能は、JDK 8 でコンパイルする必要があります。
