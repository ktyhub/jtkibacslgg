<a name="vector" href="#vector">#</a> 「ベクトル化された」クエリ処理

実験的な「ベクトル化された」クエリ実行エンジンは 0.16.0 に新しく追加されており、時系列およびグループ化 v2 クエリの 1.3-3x の範囲で速度の向上を実現できます。これは、一度に 1 行を処理するのではなく、行に対するバッチ処理の原則に基づいて動作します。行ごとではなくバッチでビットマップを反復する、バッチで列値を読み取る、バッチでフィルタリングする、バッチで値を集計するなどです。これにより、メソッド呼び出しが大幅に減り、メモリの局所性が向上し、キャッシュ効率が向上します。 これは実験的な機能ですが、私たちはこれを Druid クエリ処理の前進として捉えており、今後のリリースで不足している機能を改善して補うため、フィードバックをお待ちしています。

  • timeseries と groupBy のみがベクトル化エンジンを備えています。
  • GroupBy は、複数値のディメンションや「すべて」以外の粒度をまだ処理していません。 ※ベクトルカーソルは仮想列や降順は扱えません。
  • 式はどこでもサポートされていません。アグリゲーターへの入力として、仮想関数内、またはフィルター内ではサポートされていません。
  • 一部のアグリゲーターのみがベクトル化された実装を持っています:「count」、「doubleSum」、「floatSum」、「longSum」、「hyperUnique」、および「filtered」。
  • 一部のフィルターのみがベクトル化されたマッチャーを備えています:「selector」、「bound」、「in」、「like」、「regex」、「search」、「and」、「or」、「not」。
  • 「デフォルト」以外のディメンション仕様はまだ機能しません (抽出機能やフィルタリングされたディメンション仕様はありません)。 この機能は、クエリ コンテキストに "vectorize": true を設定することで有効にできます (デフォルトは false)。これは、Druid SQL とネイティブ クエリの両方で機能します。 true に設定すると、可能であればベクトル化が使用されます。それ以外の場合、Druid は非ベクトル化クエリ エンジンにフォールバックします。 "force" に設定することもできます。これにより、クエリが完全にベクトル化できない場合にエラーが返されます。これは、ベクトル化が実際に使用されていることを確認するのに役立ちます。 vectorSize クエリ コンテキスト パラメーター (デフォルトは 1000) を設定することで、実行中のブロック サイズを制御できます。 https://github.com/apache/incubator-druid/issues/7093 https://github.com/apache/incubator-druid/pull/6794

<a name="array-group" href="#array-group">#</a> GroupBy 配列ベースの結果行

groupBy v2 クエリでは、以前のバージョンの Druid で使用されていたマップベースの表現ではなく、結果行の配列ベースの表現が使用されるようになりました。これにより、結果セットの生成と処理が高速化されます。そのままでは、この変更は目に見えず、下位互換性があります。このより効率的な形式の利点を享受するために構成を変更する必要はなく、キャッシュされた結果には影響しません。内部的には、この形式は、ヒストリカルに対して発行するクエリでブローカーによって_常に_自動的に使用されます。デフォルトでは、結果は client に送り返される前に、ブローカーで既存の「マップ」ベースの形式に変換されます。 ただし、この変換のオーバーヘッドを回避し、さらに高速な結果を取得したい場合は、クエリ コンテキストに resultAsArray を設定して、新しい配列ベースの結果行形式を直接渡すことができます。スキーマは順番に次のとおりです。

  • タイムスタンプ (オプション; 粒度 != ALL の場合のみ) ※寸法（順）
  • アグリゲーター (順番に)
  • ポストアグリゲーター (オプション、存在する場合はその順序で) https://github.com/apache/incubator-druid/issues/8118 https://github.com/apache/incubator-druid/pull/8196

<a name="minor-compaction" href="#minor-compaction">#</a> 「マイナー」圧縮

Kafka インデックス サービスと圧縮のユーザーで、遅れたデータを少しずつ取得するユーザーは、「マイナー」圧縮と呼ばれる新しい概念の形で大幅な改善を見つけることができます。データ セグメントのバージョン管理方法の内部変更によって有効になったマイナー コンパクションは、現在の Druid ロック動作 (現在は「タイム チャンク」ロックと呼ばれています) ではなく、インデックス作成時の「セグメント」ベースのロックの考え方に基づいています。ご想像のとおり、セグメント ロックでは、圧縮されているセグメントのみをロックできると同時に、新しい「追加」インデックス作成タスク (Kafka インデックス作成タスクなど) の実行を継続し、同時に新しいセグメントを作成できます。大量の遅延データを取得する場合、これは大きな問題です。現在の動作では、優先度の高いリアルタイム タスクがロックを占有するため、圧縮タスクが枯渇することになるからです。この圧縮タスクによるデータソースのセグメント サイズの最適化が妨げられると、全体的なパフォーマンスが低下します。 セグメント ロックを有効にするには、タスク コンテキストで forceTimeChunkLock を false に設定するか、オーバーロード構成で druid.indexer.tasklock.forceTimeChunkLock=false を設定する必要があります。ただし、注意してください。この機能を有効にした後は、セグメントのバージョン管理の変更により、ロールバック パスが組み込まれていないため、0.16 にアップグレードすると、古いバージョンの Druid にダウングレードできなくなります。このため、この機能を有効にする前に、Druid 0.16 がクラスター内で安定していることを確認することを強くお勧めします。 地味な名前ですが、マイナーな圧縮の変更は奥深く、これらの release note でこれを推進するメカニズムを適切に説明することはできません。そのため、詳細については提案書と PR を確認してください。 https://github.com/apache/incubator-druid/issues/7491 https://github.com/apache/incubator-druid/pull/7547

<a name="indexer" href="#indexer">#</a> ドルイドの「インデクサー」プロセス

新しい Indexer プロセスは、MiddleManager + Peon タスク実行システムに代わるものです。インデクサーは、タスクごとに個別の JVM プロセスをフォークするのではなく、単一の JVM プロセス内の個別のスレッドとしてタスクを実行します。インデクサーは、MiddleManager + Peon システムと比較して構成と展開が簡単になり、タスク間でのリソース共有がより有効になるように設計されています。 インデクサーの利点は、クエリ処理リソース、ルックアップ、キャッシュされた認証/承認情報などを、実行中のすべてのインデックス作成タスク スレッド間で共有できるため、個々のタスクがより大きなリソース プールにアクセスできるようになり、各タスクが独自のプロセスに分離される Peon 実行モデルで可能となる冗長なアクションよりもはるかに少ない冗長アクションが実行されることです。 Indexer の使用には欠点が 1 つあります。Peon プロセスによって提供されるプロセス分離が失われるため、単一のタスクがその Indexer 上で実行中のすべてのインデックス作成タスクに影響を与える可能性があります。 druid.worker.globalIngestionHeapLimitBytes および druid.worker.numConcurrentMerges 構成は、これを最小限に抑えることを目的としています。さらに、インデクサー プロセスのタスク ログはインデクサー プロセス ログとインラインになり、ディープ ストレージには永続化されません。 サービスの開始時に org.apache.druid.cli.Main へのコマンドライン引数として server indexer を指定すると、インデックス作成の使用を開始できます。 MiddleManager および Peon の代わりに Indexer を使用するには、構成の値を Indexer 構成に適応させ、druid.indexer.fork.property. 構成を直接 Indexer に引き上げ、Peon のサイズとタスク スロットの数を乗算した値に基づいてヒープとダイレクト メモリのサイズを設定できる必要があります (MiddleManager とは異なり、構成 druid.indexer.runner.javaOpts または druid.indexer.runner.javaOptsArray は受け入れません)。詳細については、インデクサーのドキュメント を参照してください。 https://github.com/apache/incubator-druid/pull/8107

<a name="shuffle" href="#shuffle">#</a> シャッフルを使用したネイティブの並列バッチ インデックス作成

0.16.0 では、Druid の index_parallel ネイティブ並列バッチ インデックス作成タスクが、2 段階のシャッフル プロセスの実装による「完璧な」ロールアップをサポートするようになりました。 ステージ 1 のタスクは、セグメント粒度の標準時間ベースのパーティショニングに加えて行の 2 次パーティショニングを実行し、パーティションごとに中間データ セグメントを作成します。ステージ 2 のタスクには、ステージ 1 で作成されたパーティショニングのセットがそれぞれ割り当てられ、そのパーティショニングに属する中間データ セグメントのセットを収集して結合することで、最終セグメントを構築するときに完全なロールアップを実現できます。現時点では、ハッシュベースのパーティショニングのみがサポートされています。 これは、 tuningConfig で forceGuaranteedRollup を true に設定することで有効にできます。 partitionsSpec の numShards および granularitySpec の intervals も設定する必要があります。 Druid MiddleManager (または新しい Indexer) プロセスには、これらのインデックス作成タスクに対する新しい責任があり、ステージ 1 の中間パーティション セグメント出力をステージ 2 タスクに提供するため、構成とクラスター サイズによっては、ヒープ割り当てと http スレッドを増やすために MiddleManager jvm 構成を調整する必要がある場合があります。シャッフルに関与するすべての MiddleManager または Indexer プロセスは相互に通信できる必要があるため、これらの数値はクラスター サイズに応じて拡大すると予想されますが、フットプリントが現在より大幅に大きくなるとは予想していません。楽観的に考えて、既存の構成を試して、問題が発生した場合にのみヒープと http スレッド数を増やすことをお勧めします。 https://github.com/apache/incubator-druid/issues/8061

<a name="web-datasources" href="#web-datasources">#</a> データソース ビュー

<a name="web-tasks" href="#web-tasks">#</a> タスク ビュー

<a name="sql-multi-value" href="#sql-multi-value">#</a> 複数値文字列列の SQL およびネイティブ式のサポート

Druid SQL とネイティブ クエリ式の「仮想列」は、複数値文字列列を正しく利用できるようになりました。ネイティブ Druid クエリ動作と同等の個々の VARCHAR 値として操作するか、新しい複数値文字列関数のセットを使用して、または 配列のような型として操作します。これまでのところ、これはクエリ時の式でのみサポートされていることに注意してください。将来のリリースでは、transformSpec による取り込み時の複数値式の使用が可能になる予定です。追加された関数と動作変更の完全なリストはここにリストするには多すぎるため、詳細については SQL および 式 のドキュメントを確認してください。 https://github.com/apache/incubator-druid/issues/7525 https://github.com/apache/incubator-druid/pull/7588 https://github.com/apache/incubator-druid/pull/7950 https://github.com/apache/incubator-druid/pull/7973 https://github.com/apache/incubator-druid/pull/7974 https://github.com/apache/incubator-druid/pull/8011

<a name="sql-timestampdiff" href="#sql-timestampdiff">#</a> TIMESTAMPDIFF

タイムスタンプを時間単位で変更できる TIMESTAMPADD を補完するために、2 つのタイムスタンプ間の符号付き時間単位数を計算できる TIMESTAMPDIFF が追加されました。構文情報については、SQL ドキュメント を参照してください。 https://github.com/apache/incubator-druid/pull/7695

<a name="sql-time-ceil" href="#sql-time-ceil">#</a> TIME_CEIL

CEIL 関数の時間指定型でより柔軟なバージョンである TIME_CEIL も、Druid 0.16.0 に追加されました。この関数は、オプションで特定のタイムゾーンのタイムスタンプを、P3M (四半期) や PT12H (半日) などの ISO8601 期間で切り上げることができます。 追加情報については、SQL ドキュメントを参照。 https://github.com/apache/incubator-druid/pull/8027

<a name="sql-ipv4" href="#sql-ipv4">#</a> IPv4

Druid 0.16.0 には、ドット付き 10 進文字列または整数形式の IPv4 インターネット アドレスを処理するための特殊な SQL 演算子とネイテ​​ィブ式も追加されています。新しい演算子は IPV4_MATCH(address, subnet)、IPV4_PARSE(address)、IPV4_STRINGIFY(address) で、それぞれ IP アドレスと CIDR 表記のサブネットの照合、ドット付き 10 進数の文字列形式から整数形式への変換、および整数形式からドット付き 10 進数の文字列形式への変換を行うことができます。 詳細については、SQL ドキュメントを参照してください。 https://github.com/apache/incubator-druid/pull/8223

<a name="sql-nvl" href="#sql-nvl">#</a> NVL

他のデータベースでの経験を持つ Druid を使用するユーザーとの寛容性と SQL 互換性を高めるために、COALESCE 関数のエイリアスが NVL の形式で追加され、一部の SQL 方言では代わりに使用されます。 詳細については、SQL ドキュメントを参照してください https://github.com/apache/incubator-druid/pull/7965

<a name="string-sum" href="#string-sum">#</a> 文字列列の long/double/float sum/min/max アグリゲータのサポート

Long、double、float の sum、min、max のアグリゲータは、文字列列で使用する場合に許容的に動作し、ベストエフォート型の解析を実行して正しい数値型への変換を試みるようになりました。 https://github.com/apache/incubator-druid/pull/8243 https://github.com/apache/incubator-druid/pull/8319

<a name="docs" href="#docs">#</a> Web サイトのドキュメントを更新しました

Druid Web サイトのドキュメントセクションは大幅にアップグレードされ、Docusaurus の使用に移行し、現在よりもはるかに美しく機能的なページを作成します。各ドキュメント ページには、ドキュメント全体の概要を示す左側の折りたたみ可能な目次と、特定のドキュメント ページの概要を示す右側の目次があり、ナビゲーション性が大幅に向上しました。 これに加えて、取り込みドキュメントが完全に更新され、すべての重要な取り込み仕様の概念を紹介し、最も一般的な取り込み方法について説明する新しい ingestion/index.md ドキュメントが始まりました。これは、時間の経過とともに有機的に成長し、従うのが困難になった多くの既存のドキュメント ページを、より少なく、より大きく、より相互参照されたページのより単純なセットに作り直すために切望されていたものでした。また、もう少し「意見が強く」、新しい人を Kafka、Kinesis、Hadoop、ネイティブ バッチ インジェストに誘導します。彼らは Tranquility について議論していますが、事実上最小限のメンテナンス モードであるため、強く推奨されるものとしては提示していません。 これらの改善点 (およびその他の改善点) を ここ で確認してください。 https://github.com/apache/incubator-druid/pull/8311

拡張機能

<a name="datasketches" href="#datasketches">#</a> ドルイド データスケッチ

Apache Datasketches (インキュベート) 上に構築された druid-datasketches 拡張機能は、3 つの新しいポスト アグリゲータで拡張されました。quantilesDoublesSketchToRank は、指定された値よりも小さい分布の割合である指定された値のランクの近似を計算します。quantilesDoublesSketchToCDF は、ビンのエッジを定義する分割点の配列を指定して累積分布関数の近似を計算します。 デバッグを支援するために、スケッチの概要を出力する別のポスト集約 thetaSketchToString が追加されました。詳細については、Datasketches 拡張ドキュメント を参照してください。 https://github.com/apache/incubator-druid/pull/7550 https://github.com/apache/incubator-druid/pull/7937 HLLSketch アグリゲーター は、組み込みの cardinality および hyperUnique アグリゲーターと同等の機能を提供するために、値を整数に丸めることをサポートするクエリ時のみの round オプションで改善されました。 https://github.com/apache/incubator-druid/pull/8023 最後に、HllSketch のユーザーは、Druid が空のスケッチを事前計算して集約バッファーにコピーできるようにするいくつかの変更により、パフォーマンスが向上していることも確認できるはずです。これにより、クエリ処理中にアグリゲーターを初期化する時間が大幅に短縮されます。 https://github.com/apache/incubator-druid/pull/8194

<a name="stats" href="#stats">#</a> ドルイド統計

druid-stats コア拡張機能は SQL サポートによって強化され、VAR_POP と VAR_SAMP が分散アグリゲーターを使用して分散母集団とサンプルを計算できるようになりました。また、STDDEV_POP と STDDEV_SAMP が標準偏差ポスト アグリゲーターを使用して標準偏差母集団とサンプルを計算できるようになりました。さらに、VARIANCE 関数と STDDEV 関数が、それぞれ VAR_SAMP と STDDEV_SAMP のエイリアスとして追加されます。詳細については、SQL ドキュメント および 統計拡張ドキュメント を参照してください。 https://github.com/apache/incubator-druid/pull/7801

<a name="histogram" href="#histogram">#</a> ドルイドヒストグラム

druid-histogram 拡張機能の「固定バケット」ヒストグラム アグリゲーターには、新しく追加されたプロパティ finalizeAsBase64Binary があり、人間が判読できる JSON 概要ではなく、結果のヒストグラムを Base64 文字列としてシリアル化できるため、同じ拡張機能の近似ヒストグラム アグリゲーターとの一貫性が保たれます。詳細については、ドキュメント を参照してください。 https://github.com/apache/incubator-druid/pull/7784

<a name="statsd" href="#statsd">#</a> statsd-emitter

statsd-emitter 拡張機能には、druid.broker.query.time のようなメトリック名の一部ではなく、druid_service:druid/broker などの「タグ」として Druid サービス名を発行できる新しいオプション druid.emitter.statsd.dogstatsdServiceAsTag があります。 druid がプレフィックスとして使用されます。したがって、druid.broker.query.time の例は代わりに druid.query.time となり、Druid サービス タイプ全体でメトリクスを統合でき、代わりにタグによって区別されます。この設定を有効にするには、druid.emitter.statsd.dogstatsd を true に設定する必要があります。詳細については、ドキュメント を参照してください。 https://github.com/apache/incubator-druid/pull/8238 https://github.com/apache/incubator-druid/pull/8472

<a name="tdigest" href="#tdigest">#</a> 新しい拡張機能: druid-tdigestsketch

分位点などを計算し、t-digest に基づく近似スケッチ アグリゲータの新しいセットが Druid 0.16 に追加されました。 T-digest は、2 つの中間 t-digest を簡単かつ効率的に組み合わせることで、分散集約やマップ リデュース ジョブなどの並列プログラミングのユースケース向けに設計されました。これは、Apache Datasketches 拡張機能および Moments スケッチ拡張機能によって提供される既存のアルゴリズムを補完する役割を果たします。詳細については、拡張ドキュメント を参照してください。 https://github.com/apache/incubator-druid/issues/7303 https://github.com/apache/incubator-druid/pull/7331

<a name="influxdb" href="#influxdb">#</a> 新しい拡張機能: druid-influxdb-emitter

HTTP 経由で Druid メトリクスを influxdb に送信できるようにする新しい Druid エミッター拡張機能も 0.16 に追加されました。現在、このエミッタはサービス メトリクス イベントを InfluxDB に送信するだけです (メトリクスのリストについては、Druid メトリクス を参照してください)。メトリクス イベントが発生すると、イベントのキューに追加されます。設定可能な時間が経過すると、キュー上のイベントは InfluxDB の回線プロトコルに変換され、InfluxDB HTTP API に POST されます。この時点でキュー全体がフラッシュされます。エミッタがシャットダウンされると、キューもフラッシュされます。詳細については、拡張ドキュメント を参照してください。 https://github.com/apache/incubator-druid/pull/7717

<a name="tuning" href="#tuning">#</a> ワークロードを微調整する

実験的なベクトル化クエリ エンジンと新しいインデクサー プロセス タイプに加えて、0.16 には、実験を通じてインデックス作成とクエリのパフォーマンスを微調整できる可能性がある追加機能もいくつかあります。

<a name="intermediary-compression" href="#intermediary-compression">#</a> インデックス作成の中間セグメント圧縮の制御

まず、インデックス作成中に中間セグメントを永続化するときに使用する圧縮を個別に制御 (または無効化) できる機能です。この構成は indexSpec プロパティで利用でき、次のように tuningConfig に追加できます。

"indexSpecForIntermediatePersists": {
  "dimensionCompression": "uncompressed",
  "metricCompression": "none"
}

たとえば、中間セグメントの圧縮を完全に無効にします。 「非圧縮」中間セグメントを検討する潜在的な理由の 1 つは、非圧縮列からのデータの読み取りには、lz4 およびその他のエンコードされた列のデコードに使用される 64kb の直接バッファーを必要としないため、中間セグメントがパブリッシュされて深いストレージにプッシュされる前に、中間セグメントの最終マージを実行するために必要な Java 「直接」メモリーの量を軽減することです。もちろん、これはストレージ容量とページキャッシュのフットプリントのトレードオフであるため、運用ワークロードに使用する構成を決定する前に、これを試してみることをお勧めします。 https://github.com/apache/incubator-druid/pull/7919

<a name="filter-bitmaps" href="#filter-bitmaps">#</a> フィルター ビットマップ インデックス使用率の制御

通常、ビットマップ インデックスは Druid のパフォーマンスを大幅に向上させますが、シナリオによっては、特に非常に高いカーディナリティ ディメンションで計算量の多いフィルタを使用する場合、クエリ速度が遅くなる可能性があります。 Druid 0.16 では、ビットマップ インデックスをいつ使用するか、またいつフィルターを行スキャンとして実行するかを手動で制御するための新しいメカニズムが導入され、フィルターごと、クエリごとに利用できるようになりました。ほとんどのフィルターは、次のような新しいプロパティ filterTuning を受け入れます。

"filterTuning": {
  "useBitmapIndex": true
}

useBitmapIndex を false に設定すると、フィルタによるビットマップ インデックスの利用が禁止されます。このプロパティはオプションであり、filterTuning が指定されていない場合のデフォルトの動作は変更されません。この機能はユーザー向けドキュメントには文書化されておらず、実験的なものとみなされ、将来のリリースでは変更される可能性があることに注意してください。 https://github.com/apache/incubator-druid/pull/8209

<a name="request-logging" href="#request-logging">#</a> リクエストのロギング

Druid リクエスト ログを有効にしたいが、Druid SQL を使用すると、すべてのメタデータ クエリのせいで少しおしゃべりが多すぎると感じた場合は、リクエスト ログから特定の種類のクエリを選択的にミュートできる新しい構成オプションのおかげで、0.16 を使用することができます。オプション druid.request.logging.mutedQueryTypes は、Druid の ネイティブ JSON クエリ API で定義された「queryType」文字列のリストを受け入れ、デフォルトは空のリストになります (したがって、何も無視されません)。たとえば、

druid.request.logging.mutedQueryTypes=["segmentMetadata", "timeBoundary"]

segmentMetadata および timeBoundary クエリのすべてのリクエスト ログをミュートします。 https://github.com/apache/incubator-druid/pull/7562

<a name="upgrading" href="#upgrading">#</a> Druid 0.16.0 へのアップグレード

<a name="upgrading-s3" href="#upgrading-s3">#</a> S3 タスク ログ ストレージ

0.16.0 にアップグレードした後、タスク ログには、セグメントをディープ ストレージにプッシュする場合と同じ S3 アクセス許可が必要になります。これには、(バケット ACL をフェッチすることによって) バケット所有者を取得し、バケット所有者にフル アクセスを与えるためにセグメント オブジェクトの ACL を設定するための追加ロジックがいくつかあります。これらの追加のアクセス許可を提供したくない場合は、druid.indexer.logs.disableAcl=true を設定することで既存の動作を保持できます。 https://github.com/apache/incubator-druid/pull/7907

<a name="upgrading-sql" href="#upgrading-sql">#</a> ドルイド SQL

Druid SQL がルーターでデフォルトで有効になるようになりました。これにより、クエリ プランニングのデータソース スキーマを維持するために追加のメタデータ クエリが必要になるため、ブローカー プロセスにさらなる負荷がかかる可能性があることに注意してください。また、druid.sql.enable=false を設定することで以前の動作を保持するために無効にすることができます。 https://github.com/apache/incubator-druid/pull/7808

<a name="upgrading-lookup" href="#upgrading-lookup">#</a> Druid SQL ルックアップ関数

LOOKUP 関数を使用する Druid SQL クエリは、1 対 1 変換である injective ルックアップを利用するようになりました。これにより、ルックアップ評価を履歴プロセスに押し下げることを回避し、後で変換を実行できるようにする最適化を実行できます。この変更の欠点は、1 対 1 であると誤って定義されているにもかかわらず、評価時に実際には 1 対 1 変換ではないルックアップが、誤ったクエリ結果を生成することです。 https://github.com/apache/incubator-druid/pull/7655

<a name="upgrading-api" href="#upgrading-api">#</a> コーディネーター メタデータ API の変更

コーディネーターによって提供されるメタデータ API は、より一貫性のある HTTP 応答を提供するために変更されました。変更は軽微ですが、特定の API に依存している場合は下位互換性がありません。

  • ポスト /druid/coordinator/v1/datasources/{dataSourceName}
  • 削除 /druid/coordinator/v1/datasources/{dataSourceName}
  • ポスト /druid/coordinator/v1/datasources/{dataSourceName}/markUnused
  • ポスト /druid/coordinator/v1/datasources/{dataSourceName}/markUsed セグメントが変更されなかった場合、204 (空の応答) ではなく、{"numChangedSegments": N} 形式の JSON オブジェクトを返すようになりました。一方では ただし、204 (空の応答) の代わりに 500 (サーバー エラー) は返されません。
  • ポスト /druid/coordinator/v1/datasources/{dataSourceName}/segments/{segmentId}
  • 削除 /druid/coordinator/v1/datasources/{dataSourceName}/segments/{segmentId} {"segmentStateChanged": true/false} 形式の JSON オブジェクトを返すようになりました。 /druid/coordinator/v1/metadata/datasources?includeDisabled は /druid/coordinator/v1/metadata/datasources?includeUnused になりました。 includeDisabled は引き続き受け入れられますが、ログに警告が出力されます。 https://github.com/apache/incubator-druid/pull/7653

<a name="upgrading-compaction" href="#upgrading-compaction">#</a> 圧縮タスク

keepSegmentGranularity オプションは、セグメントを圧縮する前にセグメントの間隔境界を無視する圧縮タスクを作成しますが、ほとんどの場合、あまり役に立たないため、非推奨になりました。この動作が便利だと思われる場合でも、segmentGranularity を ALL に設定することで実現できます。 https://github.com/apache/incubator-druid/pull/7747 コーディネーターを介した「自動」圧縮をサポートするすべての Druid バージョンには既知の問題があり、同じ間隔で繰り返し試行すると自動圧縮が停止する可能性があります。この問題は、targetCompactionSizeBytes を設定することで 0.16 で軽減できるようになりましたが、maxRowsPerSegment または maxTotalRows を使用する場合には依然として発生します。 Druid の将来のバージョンでは、この問題は完全に解決される予定です。 https://github.com/apache/incubator-druid/issues/8481 https://github.com/apache/incubator-druid/pull/8495

<a name="upgrading-spec" href="#upgrading-spec">#</a> インデックス仕様

すべてのネイティブ インデックス作成タスク タイプは、PartitonsSpec を使用して、他のインデックス作成タスク タイプと一貫性のあるセカンダリ パーティション化を定義するようになりました。この変更には後方互換性がありませんが、ユーザーは ZZPH100​​ZZ、maxTotalRows、numShards、および partitionDimensions をネイティブ、kafka、および kinesis インデックス付けタスクのパーティション仕様に移行することを検討する必要があります。 https://github.com/apache/incubator-druid/pull/8141

<a name="upgrading-kafka" href="#upgrading-kafka">#</a> Kafka のインデックス作成

Apache Kafka インデックス サービスのセグメントの増分パブリッシングは、Druid 0.12 で導入されました。その時点では、既存の Kafka インデックス サービスは、Druid の古いバージョンからのローリング アップデートを可能にする「レガシー」形式として保持されていました。この「レガシー」コードベースは Druid 0.16.0 で削除されました。つまり、0.12.0 より古い Druid バージョンからのローリング アップデートはサポートされていません。 https://github.com/apache/incubator-druid/pull/7735

<a name="upgrading-avro" href="#upgrading-avro">#</a> Avro 拡張機能

依存関係をクリーンアップするために、fromPigAvroStorage オプションが Druid 0.16 の Apache Avro 拡張機能から削除されました。このオプションは GenericData.Array の特別な変換を提供しましたが、この列タイプはデフォルトの List 実装によって処理されるようになります。 https://github.com/apache/incubator-druid/pull/7810

<a name="upgrading-kerberos" href="#upgrading-kerberos">#</a> Kerberos 拡張機能

druid.auth.authenticator.kerberos.excludedPaths は、すべての認証者/承認者に適用される druid.auth.unsecuredPaths に置き換えられるため、代わりにこの構成プロパティを使用します。 https://github.com/apache/incubator-druid/pull/7745

<a name="upgrading-zk" href="#upgrading-zk">#</a> Zookeeper

設定 druid.zk.service.terminateDruidProcessOnConnectFail は削除され、これがデフォルトの動作になりました。Druid プロセスは、未処理の Curator client 例外が発生すると、「ゾンビ」状態で実行を続けるのではなく、終了します。 さらに、Curator client connectionTimeoutMs に接続する新しいオプション設定 druid.zk.service.connectionTimeoutMs をカスタマイズできるようになりました。デフォルトでは、Curator のデフォルトの 15000 ミリ秒が引き続き使用されます。 https://github.com/apache/incubator-druid/pull/8458

<a name="upgrading-realtime" href="#upgrading-realtime">#</a> リアルタイム プロセス

非推奨のスタンドアロン「リアルタイム」プロセスは Druid から削除されました。しばらくの間、これの使用は推奨されませんでしたが、現在では、middleManager プロセスと新しい index プロセスがすべてのリアルタイム インデックス作成タスクを処理する必要があります。 https://github.com/apache/incubator-druid/pull/7915 https://github.com/apache/incubator-druid/pull/8020
