druid 0.18.0

マイナー 公開日2020年4月20日 出典apache/druid 英語原文

#ドルイドドルイド-0.18.0 Apache Druid 0.18.0 には、42 人の寄稿者による 200 を超える新機能、パフォーマンスの強化、バグ修正、ドキュメントの大幅な改善が含まれています。 変更の完全なリスト と マイルストーンにタグ付けされたすべての項目 を確認してください。

<a name="new-features" href="#new-features">#</a> 新機能

<a name="join" href="#join">#</a> サポートに参加する

結合はデータ分析における重要な操作です。 0.18.0 より前は、Druid は SQL でのルックアップやセミ結合など、いくつかの結合関連機能をサポートしていました。ただし、これらの機能のユースケースはかなり限定されており、他の結合ユースケースでは、ユーザーはクエリ時に結合するのではなく、データを取り込むときにデータソースを非正規化する必要があり、その結果、データ量が爆発的に増加し、取り込み時間が長くなる可能性がありました。 Druid 0.18.0 は、その歴史上初めてリアル結合をサポートします。 Druid は現在、INNER、LEFT、および CROSS 結合をサポートしています。ネイティブ クエリの場合、2 つのデータソースの結合を表す join データソースが新たに導入されました。現在、left-deep join のみが許可されています。つまり、左側のデータソースには table または別の join データソースのみが許可されます。適切なデータソースの場合、lookup、inline、または query データソースが許可されます。 Druid データソースの結合はまだサポートされていないことに注意してください。同じ結合クエリ内には table データソースが 1 つだけ存在する必要があります。 Druid SQL は結合もサポートしています。 SQL 結合クエリは内部で、結合データソースを含む 1 つまたは複数のネイティブ クエリに変換されます。 SQL 変換の詳細と効率的なクエリを作成するためのベスト プラクティスについては、クエリ変換 を参照してください。 結合クエリが発行されると、ブローカーは最初に、クエリ内の唯一の table データソースであるベース データソースを除くすべてのデータソースを評価します。評価には、query データソースのサブクエリの実行が含まれる場合があります。ブローカーはすべての非ベース データソースを評価すると、それらを inline データソースに置き換え、書き換えられたクエリをデータ ノードに送信します (詳細については、以下の「ブローカーでのクエリのインライン化」セクションを参照してください)。データ ノードはハッシュ結合を使用して結合クエリを処理します。すでに存在しない限り、非プライマリ リーフ データソースごとにハッシュ テーブルを構築します。現在、事前構築されたハッシュ テーブルがあるのは lookup データソースのみであることに注意してください。結合クエリの実行の詳細については、「クエリの実行」(https://druid.apache.org/docs/0.18.0/querying/query-execution.html) を参照してください。 結合はクエリのパフォーマンスに影響を与える可能性があります。一般に、結合を含むクエリは、非正規化されたデータソースに対する同等のクエリよりも遅くなる可能性があります。 LOOKUP 関数は、ルックアップ データソースとの結合よりもパフォーマンスが向上する可能性があります。結合クエリのパフォーマンスと今後のパフォーマンス向上の計画の詳細については、結合パフォーマンス を参照してください。 https://github.com/apache/druid/pull/8728 https://github.com/apache/druid/pull/9545 https://github.com/apache/druid/pull/9111

<a name="query-inlining" href="#query-inlining">#</a> ブローカーでのクエリのインライン化

Druid は、サブクエリをインライン化することでネストされたクエリを実行できるようになりました。次の例のように、任意のタイプのサブクエリを別のタイプのサブクエリの上に置くことができます。

             topN
               |
       (join datasource)
         /          \
(table datasource)  groupBy

このクエリを実行するには、ブローカーは最初にリーフの groupBy サブクエリを評価します。サブクエリをデータ ノードに送信し、結果を収集します。収集された結果は、Broker メモリに具体化されます。ブローカーは、groupBy クエリのすべての結果を収集すると、リーフ groupBy を groupBy クエリの結果を持つインライン データソースに置き換えて、topN クエリを書き換えます。最後に、書き換えられたクエリがデータ ノードに送信され、topN クエリが実行されます。

<a name="query-laning" href="#query-laning">#</a> クエリ レーニングと優先順位付け

異種ワークロードの複数のクエリを一度に実行する場合、優先度に基づいてクエリのリソースコミットメントを制御したい場合があります。たとえば、重要度の低いクエリによって中断されることなく、重要なクエリが時間通りに実行できるように、重要度の低いクエリに割り当てられるリソースを制限するとよいでしょう。 クエリ レーニングを使用すると、異種クエリ ワークロードの容量使用率を制御できます。レーンニングでは、ブローカーはクエリを「レーン」に割り当てる目的で調べて分類します。レーンにはブローカーによって強制される容量制限があり、これを使用して、他のレーンまたは対話型クエリ (レーンなし) に十分なリソースを利用できるようにしたり、レーン内のクエリの全体的なスループットを制限したりできます。 自動クエリ優先順位付けでは、設定された戦略に基づいてクエリ優先順位が決定されます。しきい値ベースの優先順位付け戦略が追加されました。データがどのくらい過去のものであるか、クエリがカバーする間隔の大きさ、クエリに参加しているセグメントの数など、構成可能な一連のしきい値を超えるクエリの優先順位が自動的に低くなります。 詳細については、「クエリの優先順位付けとレーニング」(https://druid.apache.org/docs/0.18.0/configuration/index.html#query-prioritization-and-laning) を参照してください。 https://github.com/apache/druid/issues/6993 https://github.com/apache/druid/pull/9407 https://github.com/apache/druid/pull/9493

クエリ メトリクスの新しい次元

サブクエリを含むネイティブ クエリを部分ごとに実行できるため、新しい subQueryId が導入されました。各サブクエリには異なる subQueryId がありますが、同じ queryId があります。 subQueryId は、クエリ メトリックの新しいディメンションとして使用できます。

新しい構成

新しい druid.server.http.maxSubqueryRows 構成は、ブローカー メモリ内で実体化される行の最大数を制御します。 詳細については、「クエリ実行」(https://druid.apache.org/docs/0.18.0/querying/query-execution.html#query) を参照してください。 https://github.com/apache/druid/pull/9533

<a name="grouping-sets" href="#grouping-sets">#</a> SQL グループ化セット

GROUPING SETS がサポートされるようになり、複数の GROUP BY 句を 1 つの GROUP BY 句に結合できるようになりました。この GROUPING SETS 句は、内部で subtotalsSpec を使用して groupBy クエリに変換されます。 LIMIT 句は、各グループ化セットに適用されるのではなく、subtotalsSpec の後に適用されるようになりました。 https://github.com/apache/druid/pull/9122

<a name="dynamic-params" href="#dynamic-params">#</a> SQL 動的パラメータ

Druid は SQL の動的パラメータをサポートするようになりました。動的パラメータを使用するには、クエリ内のリテラルを疑問符 (?) 文字に置き換えます。これらの疑問符は、実行時にパラメーターがバインドされる場所を表します。詳細については、「SQL 動的パラメータ」(https://druid.apache.org/docs/0.18.0/querying/sql.html#dynamic-parameters) を参照してください。 https://github.com/apache/druid/pull/6974

<a name=" important-changes" href="# important-changes">#</a> 重要な変更点

<a name="limit-push-down" href="#limit-push-down">#</a> applyLimitPushDownToSegments はデフォルトで無効になっています

applyLimitPushDownToSegments は、クエリ可能なノードに対する下限評価をプッシュするために 0.17.0 に追加され、groupBy v2 のセグメント スキャン中の結果を制限しました。 https://github.com/apache/druid/issues/9689, で報告されているように、クエリ処理に多くのセグメントが関与している場合、これによりパフォーマンスの低下が発生する可能性があります。これは、「セグメント スキャンへのプッシュ ダウンの制限」によりセグメントごとに集約バッファが初期化され、そのオーバーヘッドが無視できないためです。この構成は、クエリに履歴タスクまたはリアルタイム タスクごとに比較的少数のセグメントが含まれる場合にのみ有効にします。 https://github.com/apache/druid/pull/9711

<a name="default-roaring" href="#default-roaring">#</a> デフォルトとしての Roaring ビットマップ

Druid は、Roaring と CONCISE という 2 つのビットマップ タイプをサポートします。ローリング ビットマップはすぐに使える優れたエクスペリエンス (一般的にクエリ速度が速い) を提供するため、デフォルトのビットマップ タイプがローリング ビットマップに切り替わりました。ビットマップの詳細については、「セグメント圧縮」(https://druid.apache.org/docs/0.18.0/design/segments.html#compression) を参照してください。 https://github.com/apache/druid/pull/9548

<a name="complex-metrics" href="#complex-metrics">#</a> SQL 互換の null 処理が無効になっている場合 (デフォルト モード)、取り込み時に複雑なメトリクスの動作が変更されます。

SQL 互換の null 処理が無効になっている場合、取り込み時の複雑なメトリック集計の動作が、クエリ時の動作と一致するように変更されました。複雑なメトリクスは、取り込み中にスキップされるのではなく、null のデフォルトの 0 値に集約されます。 https://github.com/apache/druid/pull/9484

<a name="array-expr" href="#array-expr">#</a> 配列式の構文の変更

Druid 式は、配列を作成するための型付きコンストラクターをサポートするようになりました。配列は明示的な型で定義できます。たとえば、<LONG>[1, 2, null] は、1、2、および null を含む LONG 型の配列を作成します。明示的な型を指定しなくても配列を作成できることに注意してください。たとえば、[1, 2, null] は、同等の配列を作成するための有効な構文です。この場合、Druid は要素から配列の型を推測します。この新しい構文は空の配列にも適用されます。 <STRING>[]、<DOUBLE>[]、<LONG>[] はそれぞれ、STRING、DOUBLE、LONG タイプの空の配列を作成します。 https://github.com/apache/druid/pull/9367

<a name="pending-segments-cleanup" href="#pending-segments-cleanup">#</a> 保留中のセグメントのクリーンアップをデフォルトで有効にする

メタデータ ストアの pendingSegments テーブルは、Kafka/Kinesis インデックス作成タスクや追加モードのバッチ タスクなどの追加タスク用の一意の新しいセグメント ID を作成するために使用されます。自動保留セグメント クリーンアップは 0.12.0 で導入されましたが、0.18.0 より前はデフォルトで無効になっていました。この構成はデフォルトで有効になりました。 https://github.com/apache/druid/pull/9385

<a name="better-split" href="#better-split">#</a> ネイティブの並列インデックス作成のためのより適切な入力分割の作成

並列タスクはより適切な分割を作成できるようになりました。各分割には、サイズに応じて複数の入力ファイルを含めることができます。空のファイルは無視されます。分割サイズは、新しい分割ヒント仕様で制御可能です。詳細については、「分割ヒント仕様」(https://druid.apache.org/docs/0.18.0/ingestion/native-batch.html#split-hint-spec) を参照してください。 https://github.com/apache/druid/pull/9360 https://github.com/apache/druid/pull/9450

<a name="extension-transform" href="#extension-transform">#</a> Transform が拡張ポイントになりました

Transform は、取り込み時に各行に適用される変換を表す Interface です。このインターフェイスは拡張ポイントになりました。カスタム Transform を追加する方法については、独自の拡張機能の作成 を参照してください。 https://github.com/apache/druid/pull/9319

<a name="chunk-period" href="#chunk-period">#</a> chunkPeriod クエリ コンテキストが削除されました

chunkPeriod は、用途が限られているため、0.14.0 以降非推奨になりました (groupBy v1 でのみ役立つ場合がありました)。このクエリ コンテキストは 0.18.0 で削除されました。 https://github.com/apache/druid/pull/9216

<a name="java-11" href="#java-11">#</a> Java 11 の実験的サポート

Druid は実験的に Java 11 をサポートするようになりました。Java 8 でコンパイルされた同じ Druid バイナリ ディストリビューションを Java 11 で実行できます。Travis でのテストには次のものが含まれます。

  • Java 11 を使用した単体テストのコンパイルと実行
  • Java 8 でコンパイルし、Java 11 で統合テストを実行する パフォーマンステストの結果はまだ入手できません。

Java 11 で Druid を実行する場合の不正なリフレクション アクセスに関する警告

Java 9 以降、一部のライブラリがリフレクションを使用して JDK の内部 API に不正にアクセスしていることが判明すると、警告が発行されます。これらの警告は、Druid コードを変更するか、将来のリリースでライブラリのバージョンをアップグレードすることで修正される予定です。現時点では、--add-opens や --add-exports などの JVM オプションを追加することで、これらの警告を抑制できます。詳細については、「JDK 11 移行ガイド」(https://docs.oracle.com/en/java/javase/11/migrate/index.html#JSMIG-GUID-7BB28E4D-99B3-4078-BDC4-FC24180CE82B) を参照してください。 警告の一部は次のとおりです。

<a name="pac4j" href="#pac4j">#</a> 新しい Pac4j 拡張機能

Druid プロセスの OpenID Connect ベースの認証を有効にする新しい拡張機能が 0.18.0 に追加されました。これは、同じものをサポートする任意の認証サーバーで使用できます。 【オクタ】(https://developer.okta.com/)。この拡張機能は、既存の認証サーバー内のユーザーのグループが Web コンソール を使用して Druid クラスターと対話できるようにするためにルーター ノードでのみ使用する必要があります。 https://github.com/apache/druid/pull/8992

<a name="security" href="#security">#</a> セキュリティの問題

<a name="ldap-security" href="#ldap-security">#</a> [CVE-2020-1958] Apache Druid LDAP インジェクションの脆弱性

CVE-2020-1958 が最近報告され、0.18.0 および 0.17.1 で修正されました。 LDAP 認証が有効な場合、Druid API の呼び出し元は、情報が Druid サーバーに表示される限り、credentialsValidator.userSearch フィルター バリアをバイパスしたり、LDAP サーバー上に存在するユーザーの LDAP 属性値を取得したりできます。詳しくはリンク先の説明をご覧ください。 Druid で LDAP 認証を使用している場合は、0.18.0 または 0.17.1 にアップグレードすることを_強く_お勧めします。 https://github.com/apache/druid/pull/9600

<a name="kafka-client-security" href="#kafka-client-security">#</a> Kafka client を 2.2.2 に更新します

Kafka client ライブラリが 2.2.2 に更新され、CVE-2019-12399 が修正されました。 https://github.com/apache/druid/pull/9259

Google ストレージ拡張機能は、古いタスク ログとセグメントのクリーンアップをサポートするようになりました。 0.18.0 を展開するときは、extensions ディレクトリに古いバージョンの druid-google-extensions 拡張子が存在しないことを確認してください。 https://github.com/apache/druid/pull/9519

<a name="upgrade-hadoop-aws" href="#upgrade-hadoop-aws">#</a> バイナリ配布に含まれる Hadoop AWS ライブラリ

Hadoop AWS ライブラリがバイナリ ディストリビューションに含まれるようになり、すぐに使用できるエクスペリエンスが向上しました。 0.18.0 をデプロイするときは、クラスパス内の hadoop-dependencies ディレクトリまたはその他のディレクトリに重複したライブラリがないことを確認してください。

<a name="upgrade-postgres" href="#upgrade-postgres">#</a> バイナリ配布に含まれるルックアップ用の PostgreSQL JDBC ドライバ

ルックアップ用の PostgreSQL JDBC ドライバーが、すぐに使用できるエクスペリエンスを向上させるためにバイナリ配布に含まれるようになりました。 0.18.0 をデプロイするときは、クラスパス内の extensions/druid-lookups-cached-single ディレクトリまたはその他のディレクトリに重複した JDBC ドライバーが存在しないことを確認してください。 https://github.com/apache/druid/pull/9399

<a name="known-issues" href="#known-issues">#</a> 既知の問題

<a name="inline-query-multi-value" href="#inline-query-multi-value">#</a> 複数値の列を持つ scan での topN または groupBy によるクエリの失敗

Brokers のクエリ インライン化は 0.18.0 で新たに導入されましたが、スキャン クエリで複数値のディメンションが選択されている場合、scan に加えて topN または groupBy を使用したクエリが失敗するというバグがあります。詳細については、https://github.com/apache/druid/issues/9697 を参照してください。

<a name="npe-kafka" href="#npe-kafka">#</a> Kafka インデックス サービスで Avro パーサーを使用すると、NullPointerException が発生します。

Null チェックが間違っているため、Avro パーサーは Kafka インデックス サービスでは機能しません。詳細については、https://github.com/apache/druid/issues/9728 を参照してください。

<a name="unavailable-segment-metric" href="#unavailable-segment-metric">#</a> ハンドオフ中の誤解を招く segment/unavailable/count メトリック

このメトリクスでは、リアルタイム タスクによって提供されるセグメントの数も考慮されることになっていますが、現時点では考慮されていません。その結果、実際にはすべてのセグメントがリアルタイム タスクと履歴の組み合わせで継続的に利用可能である場合でも、新しいセグメントが履歴によって読み込まれる前に可用性が急増しているように見えます。 https://github.com/apache/druid/issues/9677

<a name="sql-explain" href="#sql-explain">#</a> explain plan for クエリの結果と実際の実行プランのわずかな違い

explain plan for の結果は、クエリに結合またはサブクエリが含まれている場合、Druid が実際に実行する結果と若干異なる場合があります。違いは、explain plan for の結果では、クエリ プランの各部分があたかも独自のネイティブ クエリであるかのように表現される点にあります。たとえば、データソース d1 とデータソース d2 の groupBy サブクエリの結合の場合、explain plan for は次のようなプランを返す可能性があります。

     join
    /    \
scan    groupBy
 |        |
d1       d2

一方、Druid が実行する実際のクエリ プランは次のとおりです。

     join
    /    \
  d1    groupBy
          |
         d2

<a name="other-known-issues" href="#other-known-issues">#</a> その他の既知の問題

未解決の問題の完全なリストについては、https://github.com/apache/druid/labels/Bug. を参照してください。
