druida druida-0.18.0

Apache Druid 0.18.0 contém mais de 200 novos recursos, melhorias de desempenho, correções de bugs e principais melhorias de documentação de 42 colaboradores. Confira a lista completa de alterações e tudo marcado com o marco.

<a name="new-features" href="#new-features">#</a> Novos recursos

<a name="join" href="#join">#</a> Junte-se ao suporte

Join é uma operação fundamental na análise de dados. Antes do 0.18.0, o Druid suportava alguns recursos relacionados à junção, como pesquisas ou semi-junções em SQL. No entanto, os casos de uso para esses recursos eram bastante limitados e, para outros casos de uso de junção, os usuários tinham que desnormalizar suas fontes de dados quando ingeriam dados, em vez de uni-los no momento da consulta, o que poderia resultar na explosão do volume de dados e no longo tempo de ingestão. Druid 0.18.0 suporta junções reais pela primeira vez em sua história. Druid suporta junções INNER, LEFT e CROSS por enquanto. Para consultas nativas, a fonte de dados join foi introduzida recentemente para representar uma junção de duas fontes de dados. Atualmente, apenas a junção left-deep é permitida. Isso significa que apenas uma fonte de dados table ou outra fonte de dados join é permitida para a fonte de dados esquerda. Para a fonte de dados correta, as fontes de dados lookup, inline ou query são permitidas. Observe que a junção de fontes de dados Druidas ainda não é suportada. Deve haver apenas uma origem de dados table na mesma consulta de junção. Druid SQL também oferece suporte a junções. Nos bastidores, as consultas de junção SQL são traduzidas em uma ou várias consultas nativas que incluem fontes de dados de junção. Consulte Tradução de consulta para obter mais detalhes sobre tradução SQL e práticas recomendadas para escrever consultas eficientes. Quando uma consulta de junção é emitida, o Broker primeiro avalia todas as fontes de dados, exceto a fonte de dados base, que é a única fonte de dados table na consulta. A avaliação pode incluir a execução de subconsultas para fontes de dados query. Depois que o Broker avalia todas as fontes de dados não-base, ele as substitui pelas fontes de dados inline e envia a consulta reescrita para os nós de dados (consulte a seção "Inlining de consulta nos Brokers" abaixo para obter mais detalhes). Os nós de dados usam a junção hash para processar consultas de junção. Eles constroem uma tabela hash para cada fonte de dados folha não primária, a menos que ela já exista. Observe que apenas a fonte de dados lookup possui atualmente uma tabela hash pré-construída. Consulte Execução de consulta para obter mais detalhes sobre execução de consulta de junção. As junções podem afetar o desempenho de suas consultas. Em geral, quaisquer consultas que incluam junções podem ser mais lentas do que consultas equivalentes em uma fonte de dados desnormalizada. A função LOOKUP poderia ter um desempenho melhor do que junções com fontes de dados de pesquisa. Consulte Desempenho de junção para obter mais detalhes sobre o desempenho da consulta de junção e planos futuros para melhoria de desempenho. https://github.com/apache/druid/pull/8728 https://github.com/apache/druid/pull/9545 https://github.com/apache/druid/pull/9111

<a name="query-inlining" href="#query-inlining">#</a> Inlining de consulta em Brokers

Druid agora é capaz de executar uma consulta aninhada incorporando subconsultas. Qualquer tipo de subconsulta pode estar em cima de qualquer tipo de outra, como no exemplo a seguir:

             topN
               |
       (join datasource)
         /          \
(table datasource)  groupBy

Para executar esta consulta, o Broker primeiro avalia a subconsulta folha groupBy; ele envia a subconsulta aos nós de dados e coleta o resultado. O resultado coletado é materializado na memória do Broker. Depois que o Broker coleta todos os resultados da consulta groupBy, ele reescreve a consulta topN substituindo a folha groupBy por uma fonte de dados embutida que possui o resultado da consulta groupBy. Finalmente, a consulta reescrita é enviada aos nós de dados para executar a consulta topN.

<a name="query-laning" href="#query-laning">#</a> Caminho de consulta e priorização

Ao executar várias consultas de cargas de trabalho heterogêneas ao mesmo tempo, às vezes você pode querer controlar o comprometimento de recursos para uma consulta com base em sua prioridade. Por exemplo, você gostaria de limitar os recursos atribuídos a consultas menos importantes, para que consultas importantes possam ser executadas a tempo sem serem interrompidas por consultas menos importantes. A rota de consulta permite controlar a utilização da capacidade para cargas de trabalho de consulta heterogêneas. Com laning, o corretor examina e classifica uma consulta com o propósito de atribuí-la a uma 'lane'. As pistas têm limites de capacidade, aplicados pelo Broker, que podem ser usados ​​para garantir que recursos suficientes estejam disponíveis para outras pistas ou para consultas interativas (sem pista), ou para limitar o rendimento geral para consultas dentro da pista. A priorização automática de consultas determina a prioridade da consulta com base na estratégia configurada. A estratégia de priorização baseada em limites foi adicionada; ele reduz automaticamente a prioridade das consultas que ultrapassam qualquer conjunto configurável de limites, como o quão longe estão os dados no passado, o tamanho do intervalo que uma consulta cobre ou o número de segmentos que participam de uma consulta. Consulte Priorização e rotas de consulta para obter mais detalhes. https://github.com/apache/druid/issues/6993 https://github.com/apache/druid/pull/9407 https://github.com/apache/druid/pull/9493

Nova dimensão nas métricas de consulta

Como uma consulta nativa contendo subconsultas pode ser executada parte por parte, um novo subQueryId foi introduzido. Cada subconsulta possui subQueryIds diferentes, mas o mesmo queryId. O subQueryId está disponível como uma nova dimensão em métricas de consulta.

Nova configuração

Uma nova configuração druid.server.http.maxSubqueryRows controla o número máximo de linhas materializadas na memória do Broker. Consulte Execução de consulta para obter mais detalhes. https://github.com/apache/druid/pull/9533

<a name="grouping-sets" href="#grouping-sets">#</a> Conjuntos de agrupamento SQL

GROUPING SETS agora é suportado, permitindo combinar múltiplas cláusulas GROUP BY em uma cláusula GROUP BY. Esta cláusula GROUPING SETS é traduzida internamente na consulta groupBy com subtotalsSpec. A cláusula LIMIT agora é aplicada após subtotalsSpec, em vez de aplicada a cada conjunto de agrupamento. https://github.com/apache/druid/pull/9122

<a name="dynamic-params" href="#dynamic-params">#</a> Parâmetros dinâmicos SQL

Druid agora oferece suporte a parâmetros dinâmicos para SQL. Para usar parâmetros dinâmicos, substitua qualquer literal na consulta por um caractere de ponto de interrogação (?). Esses pontos de interrogação representam os locais onde os parâmetros serão vinculados em tempo de execução. Consulte Parâmetros dinâmicos SQL para obter mais detalhes. https://github.com/apache/druid/pull/6974

<a name="important-changes" href="#important-changes">#</a> Mudanças importantes

<a name="limit-push-down" href="#limit-push-down">#</a> applyLimitPushDownToSegments está desativado por padrão

applyLimitPushDownToSegments foi adicionado em 0.17.0 para reduzir a avaliação de limite para nós consultáveis, limitando os resultados durante a varredura de segmento para groupBy v2. Isto pode levar à degradação do desempenho, conforme relatado em https://github.com/apache/druid/issues/9689, se muitos segmentos estiverem envolvidos no processamento da consulta. Isso ocorre porque o “limit push down to segment scan” inicializa um buffer de agregação por segmento, cujo overhead não é desprezível. Habilite essa configuração somente se sua consulta envolver um número relativamente pequeno de segmentos por tarefa histórica ou em tempo real. https://github.com/apache/druid/pull/9711

<a name="default-roaring" href="#default-roaring">#</a> Rugido de bitmaps como padrão

Druid suporta dois tipos de bitmap, ou seja, Roaring e CONCISE. Como os bitmaps Roaring fornecem uma experiência pronta para uso melhor (velocidade de consulta mais rápida em geral), o tipo de bitmap padrão agora é alterado para bitmaps Roaring. Consulte Compressão de segmento para obter mais detalhes sobre bitmaps. https://github.com/apache/druid/pull/9548

<a name="complex-metrics" href="#complex-metrics">#</a> O comportamento de métricas complexas muda no momento da ingestão quando o tratamento nulo compatível com SQL está desabilitado (modo padrão)

Quando o tratamento nulo compatível com SQL está desabilitado, o comportamento da agregação de métricas complexas no momento da ingestão agora mudou para ser consistente com o comportamento no momento da consulta. As métricas complexas são agregadas aos valores padrão 0 para nulos, em vez de ignorá-las durante a ingestão. https://github.com/apache/druid/pull/9484

<a name="array-expr" href="#array-expr">#</a> Mudança na sintaxe da expressão de array

A expressão Druid agora suporta construtores digitados para criação de arrays. Matrizes podem ser definidas com um tipo explícito. Por exemplo, <LONG>[1, 2, null] cria uma matriz do tipo LONG contendo 1, 2 e null. Observe que você ainda pode criar um array sem um tipo explícito. Por exemplo, [1, 2, null] ainda é uma sintaxe válida para criar um array equivalente. Neste caso, o Druid irá inferir o tipo de array a partir de seus elementos. Esta nova sintaxe também se aplica a arrays vazios. <STRING>[], <DOUBLE>[] e <LONG>[] criarão uma matriz vazia do tipo STRING, DOUBLE e LONG, respectivamente. https://github.com/apache/druid/pull/9367

<a name="pending-segments-cleanup" href="#pending-segments-cleanup">#</a> Habilitando a limpeza de segmentos pendentes por padrão

A tabela pendingSegments no armazenamento de metadados é usada para criar novos IDs de segmento exclusivos para tarefas de anexação, como tarefas de indexação Kafka/Kinesis ou tarefas em lote do modo de anexação. A limpeza automática de segmentos pendentes foi introduzida no 0.12.0, mas foi desabilitada por padrão antes do 0.18.0. Esta configuração agora está habilitada por padrão. https://github.com/apache/druid/pull/9385

<a name="better-split" href="#better-split">#</a> Criando melhores divisões de entrada para indexação paralela nativa

A tarefa Paralela agora pode criar divisões melhores. Cada divisão pode conter vários arquivos de entrada com base em seu tamanho. Arquivos vazios serão ignorados. O tamanho da divisão é controlável com a nova especificação de dica de divisão. Consulte Especificações de dica de divisão para obter mais detalhes. https://github.com/apache/druid/pull/9360 https://github.com/apache/druid/pull/9450

<a name="extension-transform" href="#extension-transform">#</a> Transform agora é um ponto de extensão

Transform é um Interface que representa uma transformação a ser aplicada a cada linha no momento da ingestão. Esta interface é agora um ponto de extensão. Consulte Escrever suas próprias extensões para saber como adicionar seu Transform personalizado. https://github.com/apache/druid/pull/9319

<a name="chunk-period" href="#chunk-period">#</a> O contexto da consulta chunkPeriod foi removido

chunkPeriod foi descontinuado desde 0.14.0 devido ao seu uso limitado (às vezes era útil apenas para groupBy v1). Este contexto de consulta agora foi removido em 0.18.0. https://github.com/apache/druid/pull/9216

<a name="java-11" href="#java-11">#</a> Suporte experimental para Java 11

Druid agora suporta experimentalmente Java 11. Você pode executar a mesma distribuição binária Druid com Java 11 que é compilado com Java 8. Nossos testes no Travis incluem:

  • Compilar e executar testes unitários com Java 11
  • Compilando com Java 8 e executando testes de integração com Java 11 Os resultados dos testes de desempenho ainda não estão disponíveis.

<a name="new-extension" href="#new-extension">#</a> Nova extensão

<a name="pac4j" href="#pac4j">#</a> Nova extensão Pac4j

Uma nova extensão foi adicionada em 0.18.0 para ativar a autenticação baseada em OpenID Connect para processos druidas. Isso pode ser usado com qualquer servidor de autenticação que suporte o mesmo, por exemplo. Okta. Esta extensão deve ser usada apenas no nó roteador para permitir que um grupo de usuários no servidor de autenticação existente interaja com o cluster Druid, usando o Web Console. https://github.com/apache/druid/pull/8992

<a name="security" href="#security">#</a> Problemas de segurança

<a name="ldap-security" href="#ldap-security">#</a> [CVE-2020-1958] Vulnerabilidade de injeção LDAP do Apache Druid

CVE-2020-1958 foi relatado recentemente e corrigido em 0.18.0 e 0.17.1. Quando a autenticação LDAP está habilitada, os chamadores do Druid APIs podem ignorar a barreira do filtro credenciaisValidator.userSearch ou recuperar quaisquer valores de atributo LDAP de usuários que existam no servidor LDAP, desde que essas informações estejam visíveis para o servidor Druid. Por favor, veja a descrição no link para mais detalhes. É fortemente recomendado atualizar para 0.18.0 ou 0.17.1 se você estiver usando autenticação LDAP com Druid. https://github.com/apache/druid/pull/9600

<a name="kafka-client-security" href="#kafka-client-security">#</a> Atualizando Kafka client para 2.2.2

A biblioteca Kafka client foi atualizada para 2.2.2, na qual CVE-2019-12399 foi corrigido. https://github.com/apache/druid/pull/9259

<a name="upgrading-to-0.18.0" href="#upgrading-to-0.18.0">#</a> Atualizando para Druid 0.18.0

Esteja ciente das seguintes alterações entre 0.17.1 e 0.18.0 que você deve conhecer antes de atualizar. Se você estiver atualizando de uma versão anterior à 0.17.1, consulte os release notes das versões intermediárias relevantes.

A extensão de armazenamento S3 agora oferece suporte à limpeza de segmentos e logs de tarefas obsoletos. Ao implantar 0.18.0, certifique-se de que seu diretório extensions não tenha versões mais antigas da extensão druid-s3-extensions. https://github.com/apache/druid/pull/9459

<a name="upgrade-azure" href="#upgrade-azure">#</a> Extensão principal para Azure

A extensão de armazenamento do Azure foi promovida a uma extensão principal. Ele também oferece suporte à limpeza de logs e segmentos de tarefas obsoletos agora. Ao implantar 0.18.0, certifique-se de que seu diretório extensions-contrib não tenha versões mais antigas da extensão druid-azure-extensions. https://github.com/apache/druid/pull/9394 https://github.com/apache/druid/pull/9523

<a name="upgrade-google" href="#upgrade-google">#</a> extensão de armazenamento do Google

A extensão de armazenamento do Google agora oferece suporte à limpeza de segmentos e registros de tarefas obsoletos. Ao implantar 0.18.0, certifique-se de que seu diretório extensions não tenha versões mais antigas da extensão druid-google-extensions. https://github.com/apache/druid/pull/9519

<a name="upgrade-hadoop-aws" href="#upgrade-hadoop-aws">#</a> Biblioteca Hadoop AWS incluída na distribuição binária

A biblioteca Hadoop AWS agora está incluída na distribuição binária para uma melhor experiência imediata. Ao implantar 0.18.0, certifique-se de que seu diretório hadoop-dependencies ou qualquer outro diretório no caminho de classe não possua bibliotecas duplicadas.

<a name="upgrade-postgres" href="#upgrade-postgres">#</a> Driver PostgreSQL JDBC para pesquisas incluídas na distribuição binária

O driver PostgreSQL JDBC para pesquisas agora está incluído na distribuição binária para uma melhor experiência imediata. Ao implantar 0.18.0, certifique-se de que seu diretório extensions/druid-lookups-cached-single ou qualquer outro diretório no caminho de classe não possua drivers JDBC duplicados. https://github.com/apache/druid/pull/9399

<a name="known-issues" href="#known-issues">#</a> Problemas conhecidos

<a name="inline-query-multi-value" href="#inline-query-multi-value">#</a> Falha na consulta com topN ou groupBy em scan com colunas de valores múltiplos

O inlining de consulta em Brokers foi recentemente introduzido em 0.18.0, mas tem um bug que faz com que consultas com topN ou groupBy sobre scan falhem se a consulta de varredura selecionar dimensões com vários valores. Consulte https://github.com/apache/druid/issues/9697 para obter mais detalhes.

<a name="npe-kafka" href="#npe-kafka">#</a> NullPointerException ao usar o analisador Avro com o serviço de indexação Kafka.

O analisador Avro não funciona com o serviço de indexação Kafka devido a uma verificação nula errada. Consulte https://github.com/apache/druid/issues/9728 para obter mais detalhes.

<a name="unavailable-segment-metric" href="#unavailable-segment-metric">#</a> Métrica segment/unavailable/count enganosa durante a transferência

Supõe-se que essa métrica também leve em consideração o número de segmentos atendidos por tarefas em tempo real, mas não é agora. Como resultado, parece que a indisponibilidade aumenta antes que os novos segmentos sejam carregados pelos históricos, mesmo que todos os segmentos estejam realmente continuamente disponíveis em alguma combinação de tarefas e históricos em tempo real. https://github.com/apache/druid/issues/9677

<a name="sql-explain" href="#sql-explain">#</a> Pequena diferença entre o resultado da consulta explain plan for e o plano de execução real

O resultado de explain plan for pode ser um pouco diferente do que o Druid realmente executa quando a consulta inclui junções ou subconsultas. A diferença está no fato de que cada parte do plano de consulta seria representada como se fosse sua própria consulta nativa no resultado de explain plan for. Por exemplo, para uma junção de uma fonte de dados d1 e uma subconsulta groupBy na fonte de dados d2, o explain plan for poderia retornar um plano como abaixo

     join
    /    \
scan    groupBy
 |        |
d1       d2

enquanto o plano de consulta real que o Druid executaria é

     join
    /    \
  d1    groupBy
          |
         d2
